# 游戏录像格式分析

分析对象：`release/tty3d.exe`，SHA-256 `59e50674a8f57f99c3ec828fe9989a6949f47b957d630a9b3c227a780c25e4ff`，工具是 Ghidra 12.1.4。地址是这个版本 PE 的虚拟地址，函数名是 Ghidra 自动生成的。样本是游戏内录制的 `film/2026-11-13-11.16.17.tf`（8380 字节）。

结论：录像不是视频，而是客户端在录像期间收到的服务器数据包，加上镜头位置，按帧存成 XML，再加密压缩。播放时客户端把这些数据包重新喂给自己的游戏逻辑和渲染，所以不需要连服务器。启动参数 `-film` 可以直接播放，见《客户端启动参数分析》。

## 文件位置与命名

- 保存在客户端目录的 `film/` 下。
- 文件名由 `0x004a1fa0` 按 `%Y-%m-%d-%H.%M.%S.tf` 生成，即录制开始的时间。
- 录制开始和结束由界面脚本 `group/film/film_splash.h` 调用 `G_BeginFilmRecording()` / `G_EndFilmRecording()` 控制。
- 游戏内播放器是 `group/film/film_main.h`，通过 `G_GetFilmPlayer()->OpenFilm(...)` 打开录像。

## 外层：WHSC 容器

外层格式和资源包里的单个资源相同：48 字节 `whsc1.0` 头，后面跟数据。解码可以直接用 `scripts/dpk_reader.py` 里 `_decode_whsc` 的算法，只是密钥不同。

| 偏移 | 样本值 | 含义 |
|---|---|---|
| 0 | `whsc1.0` | 标识 |
| 15 | `0x03` | 标志：bit0 = zlib 压缩，bit1 = 加密 |
| 16–31 | | 明文 MD5 |
| 36 | 44501 | 明文长度 |
| 40 | 8332 | 数据长度 |

处理顺序是先解密、再 zlib 解压，最后校验长度和 MD5。

### 密钥

- 写录像的 `0x004a20b0` 和读录像的 `0x004a1880`，都用 `0x006bb824` 处的字符串 `hwh` 作为密钥，交给 `0x004a6b80` 和 `0x005d2420` 创建加密文件流。
- 加密对象设置密钥的函数是 `0x00603670`。密钥按 8 字节一组；不足 8 字节时，先把 8 字节全部填成 `0x44`（字母 `D`），再覆盖写入实际密钥。所以 `hwh` 对应的 DES 密钥是 `hwhDDDDD`。
- 资源包的密钥 `tianxiawudi` 有 11 字节，只用前 8 字节 `tianxiaw`，与工具里的实现一致。
- 加密算法是 DES-CBC，IV 为全零，不足 8 字节的尾部有特殊处理，都和 `_decode_whsc` 相同。

已验证：用 `hwhDDDDD` 解密、再 zlib 解压，长度 44501，MD5 与文件头一致。

## 内层：XML

明文是 UTF-8 编码的 XML，由 `XmlDocument::Save` 写出，换行为 CRLF。

```xml
<?xml version="1.0" encoding="utf-8"?>
<film length="236" orz="hwh" ver="0.3">
  <section>
    <loading>
      <msg_bin size="25020" value="65737 0 184552192 …"/>
      <msg_text bType="202" wPlayerScnID="965" fPlayerInitX="2428.56" fPlayerInitZ="1337.01" packet_size="20" …/>
      <msg_text bType="180" szName="小统领" bLevel="100" wEquip0="0" … packet_size="111"/>
      …
    </loading>
    <playing>
      <frame index="0">
        <camera size="16" value="0 1159186693 1082272200 …"/>
        …
      </frame>
      <frame index="7">
        <msg_text bType="131" wID="967" wAngle="185" bNow="1" packet_size="5"/>
      </frame>
      …
    </playing>
  </section>
</film>
```

| 元素 / 属性 | 含义 |
|---|---|
| `film@length` | 总帧数，样本是 236 |
| `film@orz` | 加密密钥，和外层用的 `hwh` 相同 |
| `film@ver` | 格式版本，样本是 0.3 |
| `section/loading` | 录像开始时的场景快照，播放时先用它重建场景 |
| `section/playing/frame@index` | 帧号。只有发生了事件的帧才会写出来：样本 236 帧里只有 55 个 `frame` |
| `msg_text` | 客户端知道字段结构的数据包，每个字段写成一个属性。`bType` 是包类型，`packet_size` 是原始包长度 |
| `msg_bin` | 客户端不知道字段结构的数据包，`value` 是原始字节按 32 位整数写出的十进制列表，`size` 是字节数 |
| `camera` | 镜头参数，16 字节。第 1 个整数像是参数编号，后面是 float 的位模式；具体含义没有核对 |

样本中出现的包类型。含义是根据字段名推测的，没有逐个对照代码；结合样本的补充见下文《样本内容解读》：

| `bType` | 次数 | 主要字段 | 推测含义 |
|---|---|---|---|
| 202 | loading | `wPlayerScnID`、`fPlayerInitX/Z`、`dGameTime` | 进入场景 |
| 180 | loading + 5 | `szName`、`bLevel`、`fX/fZ`、`wEquip0–7`、`wExcelID` | 角色或怪物出现 |
| 143 | loading + 2 | `wStateID`、`byStateType`、`wAutoID` | 状态 / buff |
| 133 | loading + 20 | `bFlagType`、`wData0–2`、`dwData0–1` | 对象标志变化 |
| 137 | loading | `bEquipType`、`bIdx`、`wData` | 装备信息 |
| 131 | 55 | `wAngle`、`bNow` | 转向 |
| 129 | 20 | 没有展开 | 推测为移动 / 位置同步 |
| 208、152、182、136、132 等 | 少量 | 没有展开 | 未分析 |

loading 里第一个 `msg_bin`（25020 字节）推测是自己角色的完整数据，没有解析。

## 样本内容解读

把样本里的 ID 和客户端 `mb.dpk` 中的数据表逐一对照：技能来自 `skill/skill_data_*.txt`，角色和 NPC 来自 `object/cha_list.txt`，场景来自 `scenes.json`。下表中能直接从表里查到的是确定结论，标"推测"的是根据字段和前后事件推断的。

### 出场对象

| 对象 ID | 是谁 | 说明 |
|---|---|---|
| 965 | 小统领（录制者） | 游侠，100 级，满血满蓝，初始位置 (2428.6, 1337.0) |
| 967 | 灵·玲珑塔 | 表 ID 14731，99 级，灵宠 |
| 966 | (侍)兔爷 | 表 ID 254，显示名"兔爷玩偶"，100 级，侍从，跟随录制者 |
| 44、52、68 等 | 豺 | 表 ID 25065 / 25066，1 级小怪 |
| 131 | 钟校尉 | 表 ID 4001，60 级 NPC，录像中途进入视野 |

- 场景：进入场景包里的场景 ID 是 80，`scenes.json` 对应 `fb_xiaosangcun`，即小桑村。
- loading 里 25020 字节的大包是录制者的完整角色数据：
  - 包类型 `0xC9`；
  - 偏移 67 有 UTF-8 编码的角色名；
  - 末尾有宠物名单：吊睛斑斓虎王、六尾火狐、星驰战虎、巨型黑蝎子、霞翎孔雀、兔爷玩偶。
  - 其余字段没有解析。

### 无法确定的部分

- **实际时长**：文件只记帧号，文件名和文件时间都是保存时刻，没有开始时间。如果按每秒 10 帧估算，约 24 秒，未验证。
- **镜头参数**：只在第 0 帧出现 7 组 `camera`，每组是参数编号加 float，各编号的含义没有核对。

## 可以做的事

- 读：解密解压之后就是普通的 XML，可以统计战斗过程、导出坐标轨迹等。
- 改：理论上可以改 XML，再按同样的流程压缩加密回去：zlib 压缩、DES 加密（`hwhDDDDD`），然后重写 WHSC 头的 MD5、长度和标志。改过的录像能不能被客户端正常播放，没有测试。
