# 修改队列批量写包

右上角修改队列的「应用修改」通过 `POST /api/package-queue/apply` 一次提交全部项目。目前包括跨职业技能、职业技能配置、召唤物、骑宠设置，以及一件或多件新增武器。

## 执行过程

1. 读取客户端共享工作包，检查服务器主包、动态包的共享缓存。远端内容未变化时复用缓存。
2. 在一个临时目录中准备三份工作包。按照队列顺序叠加修改，每一项都读取前一项的结果，避免修改同一张表时相互覆盖。若多个项目修改同一字段，以排在后面的项目为准。
3. 校验每项的职业、技能、骑宠、词条、模型等数据。新增武器使用当前三份临时包的全部物品 ID 分配新 ID，因此多件武器不会分配到相同 ID。全部项目完成后再次校验新增武器记录。
4. 再次核对远端包的原始指纹。每个有变化的服务端包只上传一次、备份一次、替换一次；在确认提交前校验服务端文件的 SHA-256。主包和动态包各自保留原有表结构，不互相整包覆盖。
5. 使用已经准备好的文件，最后一次性更新客户端持久工作包及服务端共享缓存，保存跨职业来源信息和召唤物设置。客户端下载最终的一份 `mb.dpk`。
6. 清理临时目录。根据队列项目提示执行热重载或手动重启。队列全部成功且所有项目都支持热重载时，完成弹窗提供「转到热重载」按钮；点击进入「运维管理 → 服务控制」，清除先前选择并自动勾选本次项目对应的热重载标签，再由操作者点击「重新载入」。如果本次队列包含需要重启的项目，则提供「转到服务控制」按钮，跳转并定位到服务控制卡片，由操作者手动点击「重启服务端」。

现有逐表补丁函数在临时目录中仍可能产生中间 DPK；它们不会逐项写回持久工作包或服务器。这次优化减少的是每项单独提交、传输、备份及替换整包的次数，并保留不同补丁的原有布局与校验规则。

批处理还会跳过不必要的压缩参数搜索：如果补丁已允许当前方向的块链扩展或缩减，直接使用正常压缩结果，不再为了维持原块数遍历数百种压缩参数。禁止缩减或扩展的情形仍执行原有检查；每次写包后的结构、解码及内容回读校验均保留。

## 失败处理

- 任一项目生成或校验失败时，不发布这次队列；客户端持久工作包及服务器原包不变，页面保留完整队列供修改和重试。
- 如果远端包在生成或上传期间被其他程序修改，停止提交，不覆盖这些新内容。
- 磁盘包替换过程中若失败，尝试恢复这次提交前的磁盘包备份。此处是文件提交保护，与「热重载失败不恢复运行时旧表」的规则分开；队列不会自动热重载或自动重启服务端。
- 服务器同步成功后，若本地文件最终替换异常，返回已提交结果并保留剩余文件到 `data/package-queue-recovery-*`，提示具体位置，避免重复新增武器。

实现：`scripts/package_queue.py` 负责本地按序合并，`gm_server.py` 的 `apply_package_queue` 负责统一发布，`index.html` 负责一次请求、运行计时和最终下载。

## 验证记录

2026-10-27，使用本机现有客户端工作包、服务器主包及动态包，在临时目录离线叠加职业技能、跨职业技能、召唤物、骑宠设置及两件新增武器，共 6 项。输出中的学习职业、技能冷却、骑宠速度和两件武器记录均校验通过；新武器 ID 连续且不冲突，原始三份包的 SHA-256 未变化。

相同样例在跳过不必要的压缩参数搜索前约 82.6 秒，优化后约 11.1 秒，不含网络上传和服务器替换耗时。已通过 21 项自动化测试，其中包含统一上传、生成失败、同步失败、最终本地更新异常和接口访问限制。未向运行中的服务器提交这次离线测试产物。
