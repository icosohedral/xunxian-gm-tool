# 技能热重载（reloadskill）

## 使用方式与范围

修改并保存技能配置后，在「技能配置」顶部点击「热重载技能」，确认后将服务器当前主包中的技能表加载到普通线（1）与交易线（9）。该操作不重启服务端，不修改技能数值，也不生成新的客户端包。

「运维管理 → 服务控制」使用多选标签。一次可以选多个范围；工作台先合并标签对应的表清单，再从同一份主包构建一次重载包。重复表 ID 会去重并排序，在普通线与交易线的命令阶段复用原生 GM 连接。交叉职业表、召唤物范围或骑宠范围有交集时，同一张表只发送一次 `reloadexcel`；若包含职业技能定义，只执行一次 `reloadskill`。商城使用专用 `reloadxyshopitem` 命令；服务器帮助目前只确认 `reloadexcel <单个表ID>` 语法，因此每个唯一表 ID 仍单独发送。合并处理减少重复解包、传输和连接开销，不把多个 ID 拼成未经验证的命令。

服务控制中的所有热重载范围统一采用同一失败处理：清理本次临时散文件，但不恢复运行中的旧表，也不自动重启服务端。若普通线与交易线出现部分成功，线路状态可能不一致，由操作者决定后续处理。

本功能已扩展为按当前子标签重载：

| 当前子标签 | 服务端范围 | 客户端操作 |
| --- | --- | --- |
| 职业技能配置 | 原生 `reloadskill` 的 45 张技能定义表 | 替换包并重新登录 |
| 跨职业技能 | `reloadexcel 210`、`reloadexcel 211`，重载导师列表和学习条件 | 替换包，重新登录后打开导师窗口 |
| 服务控制：技能定义表热重载 | 原生 `reloadskill` 的 45 张技能定义表 | 替换包并重新登录 |
| 服务控制：技能学习表热重载 | `reloadexcel 211`，只重载技能学习条件表 | 替换包并重新登录 |
| 服务控制：骑宠设置 | `reloadexcel 84`（乘骑连接）和 `reloadexcel 85`（骑宠列表） | 应用服务器主包中的骑宠设置；已有骑乘建议下坐骑后重新骑乘 |
| 服务控制：商城 | `reloadxyshopitem`，重建商城配置并刷新在线商城 | 上架、单件下架和批量下架保存后自动尝试；也可在服务控制手动重载 |
| 服务控制：新增武器 | `reloadexcel 41`，重载 `item/item_list.txt`、`item/item_list2.txt`、`item/item_list3.txt` | 替换客户端包并重新登录；之后再次发放新武器 |
| 召唤物 | 校验 52 张关联表；重载 209、210、211、500、1351、1352，再执行 `reloadskill`；角色表 82 只在发现变化时重载 | 先收回召唤物或退出客户端；替换包后重新登录并重新召唤 |

成功的热重载不主动重启服务端。新增武器使用下文的表 41 专用流程；其他物品定义仍不在热重载范围内。客户端职业分表通过替换客户端包刷新，当前服务器实际载入的表 202 为 `skill/skill_cha.txt`，不能把 `skill_cha_yx/ls/fs/fzs.txt` 与它混为一谈。

下文中的 45 张表及 `reloadskill` 流程描述的是技能定义基础范围。关联表在同一操作中暂时部署到 `mb/object/`、`mb/skill/`、`mb/summon/` 各自原有路径，通过白名单 `reloadexcel 表ID` 加载。新增了关联表的整数数组与字符串回读，检查导师技能、召唤技能 ID 与顺序等字段；空数组按原生缺省值处理。所有范围失败后都只清理本次临时散文件，不恢复运行中的旧表，也不自动重启服务端。

骑宠热重载使用相同的服务器版本、线路身份和内存回读检查。服务端主包提取 `object/ride_connection.txt`（表 84）与 `object/ride_list.txt`（表 85），临时写入原生读取路径后，依次对普通线与交易线执行两条 `reloadexcel` 命令，再校验两张表的行数和配置字段，并清理本次临时散文件。失败时不会恢复运行中的旧表，也不会自动重启；普通线、交易线之间若出现部分成功，线路状态可能不一致。已存在的乘骑对象可能缓存了创建时的配置，修改后建议先下坐骑再重新骑乘。

新增武器热重载单独使用表 41，因为主包索引把三张 `item_list` 资源合并为一张表，不能按单文件表处理。实现会核对三份服务器散文件、表 41 行数、所有物品 ID，以及样本行和新增物品的关键字段；普通线和交易线分别执行一次 `reloadexcel 41`。此流程**不恢复运行中的旧表，也不自动重启服务端**。若失败后线路间状态不一致，由操作者决定是否手动重启。工作台只清理本次临时散文件，不会恢复已修改的服务器主包或动态包。成功后仍要替换客户端 `mb.dpk`、重新登录，再发放新武器验证。

商城使用服务端散文件 `/opt/xxserver/runtime/xx/shm/TTYGZS/dynamicmb/xy_shop_item.txt`，该文件不在当前主包或动态包的 `index_list.txt` 中，因此不能用 `reloadexcel 表ID` 直接重载。服务端二进制提供 `reloadxyshopitem`：命令先调用 `ReloadTable(67)`，再执行 `CShopMngS::XYShopDestroy()`、`XYShopBuild()` 和 `XYShopReload()`。普通线、交易线的帮助均确认该命令可用，成功回执为 `reload xy_shop_item OK!`。工作台保存上架或下架修改并回读文件后，会对两条线路执行该命令；服务控制也提供「商城」标签供手动重载。失败时保留已保存的商城文件，不恢复运行中的旧商城、不自动重启，并显示错误；如果两条线只成功一条，商城状态可能暂时不一致。

原生命令会先调用 `DelAllSkillAndMehtodUnit()`，清理场景中正在运行的技能、效果单元，然后重建技能相关数据。操作前应结束战斗；不承诺已有冷却计时、召唤物或客户端界面随之刷新。

## 调用流程

1. 工作台通过本机受限的 `POST /api/skills/reload` 接口进入操作，与其他写包操作共用锁。
2. 使用已有服务器包共享缓存；远端指纹和 SHA-256 一致时不重复下载。热重载只从服务器主包提取数据，不从客户端包导出服务器技能表。
3. 根据主包 `index_list.txt` 检查原生表 ID、路径、载入类型及起始行，提取完整的 45 张技能表。保留原始字节、列布局、编码和空表头行。
4. 校验服务器程序版本、两条线路进程身份、磁盘优先读取模式及内存表的实际资源路径，记录操作前的表行数和整数单元值摘要；用 `help reloadskill` 验证命令通道。
5. 再次核对远端主包 SHA-256，将技能表暂时部署到 `/opt/xxserver/runtime/xx/shm/TTYGZS/mb/skill/`。写入采用同目录临时文件、刷新、原子替换及 SHA-256 回读。若原位置存在其他来源且内容不一致的散文件则拒绝覆盖。
6. 经 SSH 在服务器本机连接原生 GMS 管理端口 `127.0.0.1:3000`，分别发送 `gmcmd_2_gzs 1,reloadskill`、`gmcmd_2_gzs 9,reloadskill`。指令经游戏原生队列执行，不向游戏进程写内存，不从外部线程调用游戏函数。
7. 校验两条线路回执及运行内存。45 张表的行数必须一致；校验各行整型索引、整型冷却及距离字段，并抽查首、中、末行整型单元。两条线路 PID 与进程启动标识必须保持不变。
8. 成功或失败后清理本次临时散文件，避免它们在后续写包或重启时遮蔽主包内容。失败后不重新发送旧表、不恢复运行中的旧表，也不自动重启服务端；普通线与交易线若出现部分成功，由操作者决定如何处理。服务器状态目录仍记录最近一次成功加载的内容和进程信息。

现有进程可能仍打开写包前的 DPK 文件描述符，直接发送命令会读到旧包。此版本文件管理器模式为 2，读取顺序是磁盘文件优先、包文件其次，因此临时散文件能让原生加载器读取当前主包的数据。完成后删除散文件不影响已经载入内存的数据。

## 原生命令执行内容

经本机服务端二进制核对，入口为 `CServerCmd::_i_srad_reloadskill`，主要执行：

- 清理场景技能与效果单元。
- `CMethodGroupDataMng::ReloadSkillTable()`：重读 45 张技能相关表。
- `CMethodDataMng::LoadMethod(1)`、`LoadMethodUnit(1)`。
- `CMethodGroupDataMng::Load()`、`ReloadPassive()`。

原生返回成功文字为 `ReloadExcel:OK!`。这个函数会覆盖部分中间错误文字，所以实现没有仅凭回执认定成功，而是增加了运行内存校验。内存校验能证明表数据已载入，不能替代每个技能在游戏中的施放验收，也不等于完整校验所有派生缓存。

## 失败恢复与文件保留

部署记录位于 `/opt/xxserver/state/gmtool-skill-reload/`：

- `current.json`：最近一次成功热重载的数据及对应进程身份，只有一份。
- `previous/`：最近一次成功事务的操作前备份，后续成功时替换，仅保留一份。
- `transaction-*`：失败事务的恢复依据。失败时保留并在错误信息中给出路径，以便检查未完成的恢复。

写文件失败时恢复原始散文件。已经尝试重载的事务失败时，恢复先前技能来源，并对两条线路重新执行原生命令，再比较操作前后的内存摘要。若之前有同一组进程成功热重载的记录，使用该记录的数据恢复；首次操作则恢复原散文件，让原生加载器回到原来的包来源。恢复完成后清理临时覆盖文件。

若线路中途退出、进程变化或恢复校验不一致，会明确报告恢复未完成。此时不能把错误当成成功，需先检查服务器运行状态与备份。命令清理过的运行中技能效果无法通过恢复配置找回。

## 协议与版本约束

协议帧为 `AA55 + 小端 uint32 正文长度 + 正文 + 55AA`。握手正文为 `F1 + uint32(0)`；预期回应为 `FB 01 0A 00 00 00`。请求正文为 `F2 + uint32 请求标识 + 00 + ASCII 命令 + 00`；回应以 `FC` 开头，包含同一标识及 GB18030 文字。实现限制长度、超时、命令和线路，只暴露 `reloadskill`、关联表白名单的 `reloadexcel` 及其帮助检查。技能和骑宠范围按各自固定表 ID 限定；新增武器专用流程只允许表 41。

内存回读布局仅适用于已核实的 32 位服务端：

| `TTYGZS_d.so` | `9a19e9c8deaefeb8ba35d61f10ccc6f32d166ef2ee2aedf1f3ecf06cfa7109bb` |

版本不匹配会拒绝执行，不能直接删除版本校验来兼容其他服务端。SSH 用户需具备现有管理配置所使用的免交互 sudo 权限；远程依赖 Python 3 以及 `/proc` 只读内存访问。

本地实现为 `scripts/skill_reload.py` 和 `scripts/skill_reload_agent.py`。自动化验证命令：`python -m unittest discover -s tests -v`。

## 骑宠设置热重载

当前服务器运行时检查确认普通线与交易线均已加载表 84（326 行）和表 85（449 行），并指向 `mb/object/ride_connection.txt` 与 `mb/object/ride_list.txt`。服务控制的“骑宠设置”热重载会校验主包来源、临时部署两张表、依次执行 `reloadexcel 84` 与 `reloadexcel 85`，并回读两条线路的行数及字段。此流程尚未在运行服务器上执行真实重载；在线骑乘对象是否立即刷新仍需实际游戏验证。

## 新增武器热重载

服务器主包索引将三张物品列表定义为表 41。当前普通线和交易线均从 `mb/item/item_list.txt`、`item_list2.txt`、`item_list3.txt` 读取该表，合计 41,401 行。`CItemMngBase::GetExcel(int)` 通过 `CExcelTableMng::SafeGetLine(41, item_id)` 按物品 ID 查表，因此原生重载后，后续物品查询可访问新行。动态包索引中的表 41 仅登记 `item/item_list.txt`，本流程以运行中主包的三文件来源为准。

服务控制的“新增武器”会先验证表 41 的三资源索引与当前运行时来源，再暂时把主包三张表放到服务器散文件读取路径，逐线路执行 `reloadexcel 41`，最后校验行数、全部物品 ID 及新增武器字段。失败不回滚旧运行时表、不执行重启；错误提示和操作日志会显示失败信息。工作台仅清理本次临时文件。此实现尚未在运行服务器上执行真实重载，也未完成游戏内发放验收。

## 已确认的共用入口

当前服务端存在原生命令 `reloadexcel 表ID`，入口 `CServerCmd::_i_srad_reloadexcel`（`TTYGZS_d.so` 相对地址 `0x985b20`）。它调用 `CExcelTableMng::ReloadTable(int)`（`0xc614ea`），再调用 `MBCfgMngs::ReloadExcel(int, bool)`。

`MBCfgMngs::ReloadExcel` 在当前版本仅对 1620（在线奖励）有额外刷新分支，不能假定它会为学习、NPC 或召唤物自动重建派生缓存。

`CExcelTable::Reload()`（`0xc60d98`）先 `RemoveAll()`，再按记录的资源路径载入并创建索引。因此失败时不能只恢复磁盘文件，还必须重载旧数据并验证内存；也必须检查使用者是否长期持有旧行指针。

可以复用现有 GMS 本机管理协议、游戏主线程命令队列、服务器包共享缓存、临时散文件覆盖、版本校验及事务恢复框架。扩展时只增加固定的表 ID 白名单，不开放任意管理命令。

### 建议实现

1. 完成现有写包与回读校验。
2. 从服务器当前主包提取 211、210 对应的原始文件，临时部署到已核实的磁盘覆盖路径。
3. 对普通线和交易线分别执行固定的 `reloadexcel 211`、`reloadexcel 210`。
4. 验证表行数、目标技能的职业字段，以及导师技能数组内容。现有重载器只检查整型单元，必须增加数组内容检查，不能只检查行数。
5. 成功后清理临时文件；任何一步失败时，两张表与两条线一并恢复。
6. 玩家替换客户端包并重进，重新打开导师窗口，再学习目标技能。

只调整学习规则时不必额外执行 `reloadskill`；如果同次操作也新增或修改技能定义，再合并执行。取消允许学习不会自动删除角色已经学会的技能，这属于另一项角色数据操作。

## 召唤物自定义

### 表与实例的关系

| 文件或表组 | 表 ID | 处理思路 |
| --- | --- | --- |
| 游侠、NPC 的技能、方法、触发表等 | 现有 45 张技能表范围 | 使用已实现的 `reloadskill` |
| `object/cha_skill_choose.txt` | 500 | 修改自选技能组后定向重载 |
| `summon/summon_skill.txt` | 1351 | 修改默认技能、技能栏顺序后定向重载 |
| `summon/summon_skill_index.txt` | 1352 | 新增技能索引时定向重载，并替换客户端包 |
| 学习、导师、升级表 | 211、210、209 | 只有实际发生相关变更时重载 |
| `object/cha_list.txt` | 82 | 仅补入原本缺失的导师角色记录时需要；应单独验证角色缓存影响 |
| `object/cha_fight.txt`、分身战斗属性表 | 88、1435 | 当前召唤自定义通常不改这两张表，无需为了切换召唤物而重载全部属性 |

代码证据：

- `CCha::ListNpcSkill()`（`0xae855a`）查询角色表 82，根据外形读取技能选择表 500，将技能 ID 放入角色实例的 `std::vector<int>`。技能组是实例持有的数据，不能认为重载表 500 就立即更新已经召出的角色。
- `CCha::ListNpcSkillUnit(int)`（`0xae8462`）还会访问技能单元表 501，支持技能组中的间接引用。当前自定义通常修改 500；只有实际修改 501 时才应将其纳入重载范围。
- `CServerCha::InitSummonStraw(CServerCha*)`（`0x9189a2`）按召唤物战斗能力 ID 查询表 1351，设置默认技能与手动技能列表。因此新召唤实例有读取新技能栏配置的入口。
- `CChaDataMngBase::GetExcel()`（`0xaf336e`）按角色 ID 查询表 82；`CNpcDataMngBase::GetFightDataInt(int)`（`0xb2b072`）存在读取 88 与 1435 的分支。仍不能据此认定所有属性缓存都会自动刷新。
- 当前 `_ensure_friend_cha_list` 在导师记录已存在且外形一致时直接返回原数据，缺失时才补入；它不负责重写所有 NPC 属性。

### 建议实现

1. 玩家先退出客户端，或至少收回召唤物并结束战斗。
2. 记录本次实际修改的资源清单，区分客户端资源与服务器已加载资源，避免盲目重载所有表。
3. 暂时部署本次需要的散文件；对普通线和交易线重载技能选择与技能栏等关联表，再执行 `reloadskill` 重建技能定义与方法数据。涉及表 82 时单独处理，不能直接宣称与技能表同样安全。
4. 验证选择技能 ID、技能栏数组顺序、冷却、召唤触发器关联角色 ID，以及涉及的角色记录均与主包一致。表 1352 含字符串和图标字段，需扩展相应校验，不能只依赖现有整数检查。
5. 清理临时散文件并保存最近一次完整成功状态；失败时恢复整个关联表组及两条线路。
6. 玩家替换客户端包，重新登录并重新召唤，让新的召唤物实例初始化技能组和技能栏。此流程不要求已有召唤物原地更新。

该方案不会因为重载配置而给怪物增加新的 AI 逻辑；仍使用当前自选技能方案。也不应自动全服收回其他玩家的召唤物。

## 验证次序与未完成事项

优先验证跨职业两张规则表：范围小，学习处理函数直接查询它们。选一个角色尚未学会的技能，验证“允许后可学习”，再用另一个未学技能验证“取消后不能学习”，同时确认两个游戏进程未重启。

随后验证切换到已有角色的召唤自定义：检查外形、技能组、技能栏顺序和冷却，并确认重新召唤后使用新配置。最后再测试需要向表 82 补入新导师记录的情况，排查其他 NPC 对旧表行的引用。

本次证据来自工作台修改代码、服务端符号与反汇编及运行内存路径检查。数组/字符串校验、关联表事务恢复现已实现，跨职业、召唤物部分失败恢复均有自动化测试。现有角色配置的实际重载与内存校验已通过；角色真实学习、施放及重新召唤后的游戏表现尚需客户端验收。表 82 当前与主包一致，实际测试未触发其重载；补入全新导师角色的分支尚未做运行验收。

服务端版本约束沿用《技能热重载实现说明》中的四个二进制 SHA-256，不应在未核实其他版本时直接照搬地址或表布局。
