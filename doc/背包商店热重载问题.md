# 背包商店商人缓存热重载

`reloadexcel 50,95` 只刷新商品表和商人表，不重建 `CMerchantMngS` 已创建的 `SMerchandise` 链表。此前因此出现配置已保存，但上架、下架要重启游戏服务才生效的问题。

## 当前实现（2026-10-28）

工作台在保存商人散文件、重载配置表后，运行 `scripts/native/merchant_hot_reload_agent.py`。它检查游戏二进制版本、线路进程和跟踪器身份，编译固定版本的 32 位模块 `scripts/native/merchant_refresh.c`。通过现有跟踪器临时交接调试权限，在游戏进程内调用模块，依次重建商人 238、239、283、284、285 的商品链表，并维护全局补货列表。随后重新附加跟踪器，回读两条线路的商人缓存，核对本次上架和下架的商品 ID。没有通过核对时，接口明确报告未生效。

原生模块使用游戏自身的商品构造、初始化和析构函数。初始化失败的商品按游戏启动时的行为跳过；因此表 95 中存在无效商品时，保存配置与运行中列表可能持续不一致。已打开商店的角色需要关闭并重新打开，才能收到新商品列表。刷新会重建目标商人的商品及库存状态。代码与当前 `TTYGZS_d.so` 哈希绑定，更换游戏二进制后须重新分析与适配。

## 验证记录

在正式两条线路上，测试商品 2032 加入 VIP1 商人 238 后，单独执行 `reloadexcel 50,95` 时，两条线路的运行中缓存仍无此商品。调用原生刷新后，两条线路的商品数各由 54 变为 55，均包含 2032；再从配置下架并通过工作台自动刷新后，均恢复到 54 且不包含 2032。上架和下架期间，两条游戏线路的 PID 均未变化。测试商品已从配置移除。

开发过程中安装 GDB 同时升级了系统 libc，导致旧跟踪器与磁盘 libc 版本不一致，一次调试调用终止了世界线并触发服务整组关闭。已重新启动并恢复两条线路，之后加入了跟踪器已加载 libc 与当前文件一致的检查，遇到不一致会拒绝刷新。该次开发期间曾重启服务；上述上架、下架验证是在恢复后的同一组游戏进程内完成的，无需重启。

售价变更会重建商品对象，但目前仅核验商品列表的增删结果，没有从游戏客户端验证最终显示的售价。已打开商店的显示、购买中的交易、补货过程和二进制版本变化也没有进行端到端验证。

## 客户端商品表（2026-10-28 补充）

上架后商人缓存核对通过、商品却无法在游戏内购买，原因是客户端同样持有自己的 `item/item_mcht.txt`。客户端按商品 ID 从本地商品表解析物品与折扣（`tty3d.exe` 的 `GetShopTipFromMchtID`），再用本地 `item/item_list*.txt` 的购买价格乘折扣显示售价；服务端散文件里的新商品在客户端没有对应记录，因此无法定价、无法购买。

判断依据：

- 客户端 `object/npc_mcht.txt` 中商人 238 只有 26 个商品，而游戏内实际显示 54 个，其中 27867（二级返虚符）不在客户端的 26 个之内，说明商人商品列表由服务端下发，客户端的商人表不参与显示。
- 客户端 `item/item_mcht.txt` 有 4210 行，包含 27867，但所有通过工作台上架的商品（28786–28791、28704–28712、28723 等）都不在其中。
- 工作台改写物品基础购买价时只写入服务端主包，客户端仍是旧价。例如物品 21532 服务端已改为 10000 铜，客户端仍是 2800000 铜。

现在的处理：上架时在服务端热重载之后，把商品记录（商品 ID、物品 ID、文字说明、金币折扣）追加到 `data/client_mb_work.dpk` 的 `item/item_mcht.txt`，并把同一批物品的基础购买价写入客户端 `item/item_list*.txt`，随后回读校验。已保存商品可通过「同步客户端」按钮一次性补齐，写入后需下载客户端包替换游戏目录中的 `mb.dpk` 并重新登录。

## 上架走修改队列（2026-10-28 补充）

背包商店的上架不再即时写入，而是先攒清单、再进右上角的修改队列，只有执行队列时才落盘：

- 前端「加入清单」只把物品、售卖范围、售价暂存在页面里（`state.backpackDraft`，同一物品重复加入会覆盖），不调用任何接口。
- 「全部加入执行队列」把清单每一项作为一个 `kind: "backpack"` 的队列项推入 `dpkQueue`，`key` 为 `backpack:<物品 ID>`，因此可以连续加入多件；`weapon` 与 `backpack` 是允许重复出现的两类。
- 点「应用修改」调用 `/api/package-queue/apply`，由 `PackageQueueBuilder._patch_backpack` 逐项处理：
  - 用 `prepare()` 在内存中累积 `item/item_mcht.txt`、`object/npc_mcht.txt` 的改动（第一个背包项时读一次远端散文件）；
  - 原价与折扣无法表示填写售价时，用 `initialize_item_price()` 改写 builder 里的服务端主包副本（第 16 列），价格随主包一起发布；
  - 用 `backpack_client.apply()` 把商品行与基础购买价写进 builder 里的客户端包副本，并回读校验。
- 服务端包发布完成后，`apply_package_queue` 用 `reload_remote()` 一次性提交两份散文件、热重载表 50/95（补过基础价时额外 `reloadexcel 41`）、刷新原生商人缓存并回读核对；失败时整体回滚并在结果里给出警告，已发布的包不回退。
- 队列执行完成后由既有流程自动下载最终客户端 `mb.dpk`。背包项标记为不可热重载（`reloadable: false`），因为它已经在队列里完成了热重载，不需要再去「服务控制」重复操作。

散文件不在包里，所以这一步只能排在服务端包发布之后：`reload_remote()` 需要拿到发布后主包的 sha256 作为并发校验基线。价格初始化改的是主包本身，因此必须在发布前完成，否则会出现包与散文件价格不一致。

本轮同步结果：新增 15 条商品记录，其中 28786、28787、28788、28790、28791 共 5 件为正常商品；改写 3 个物品购买价（21532、49983、49985）；客户端原有 4210 行商品记录全部保持不变，包体积不变，697 个资源均可正常解出。仍有 10 件 SVIP 商品（28704–28712、28723）引用物品 3665–3673、3678，这些物品在服务端和客户端的物品表中都不存在，服务端初始化时已跳过，无法购买，需要换成有效物品或从商店下架。

### 为什么不把商品表改成「仅服务端加载」

`index_list.txt` 第 6 列是使用类型：`0` 服务器和客户端都加载、`1` 仅服务器、`2` 仅客户端、`3` 都不加载。当前登记：

| 备注 | 索引 | 文件名 | 使用类型 |
| --- | --- | --- | --- |
| 道具列表 | 41 | `item/item_list*item/item_list2*item/item_list3` | 0 |
| 商品道具 | 50 | `item/item_mcht` | 0 |
| NPC商人 | 95 | `object/npc_mcht` | 0 |

客户端包共登记 1047 张表，其中仅服务端 443 张、两者都加载 383 张、都不加载 118 张、仅客户端 103 张。仅服务端的例子是掉落表、衍生表、GM 测试表这类纯服务端逻辑表，商品表不在其中。

客户端把第 50 表整行解析（`ttygzs.so` 中的列名枚举 `ItemMcht_ID/ExcelID/MaxNum/Group/Restore/CampID/…/MoneyPoint/Merit/Discount/…`），商店窗口按服务端下发的商品 ID 用本地行取物品与折扣。把客户端包的这一列改成 `1`，客户端就不建这张表，`GetExcel(50, id)` 一律返回空，受影响的不是新商品而是全部商品，商店会出现空行、价格为 0 或点不动，甚至可能因空指针崩溃。改服务端包的这一列则只影响服务端自己（服务端仍需该表），对客户端毫无作用。

要让客户端不依赖这张表，得让商人列表协议直接下发物品、折扣和售价，属于改客户端与协议的工作量，不是改一个登记值能解决的。
