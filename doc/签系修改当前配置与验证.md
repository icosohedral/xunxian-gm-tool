## 作用范围与部署

武器为掠夺者之剑 `60075`。签系相关测试效果依赖当前版本服务端的进程内钩子，两条线路均已加载，并已安装开机自动恢复服务；该服务检测到两条线路进程重启后会尝试重新加载，实际再次重启验证尚未完成。不能仅凭源码或客户端包判断效果已经生效。原武器 `60074` 的目标最大生命值百分比伤害与吸血保留，不再承担本页所列武器绑定的签系效果。

## 一键三召唤与技能距离

使用签系召唤技能时补齐签兵、签将、签王，原则上每种各 1 个。95 级甲签 `3093` 使用角色 `2460`，之前因识别范围遗漏而只出现签将，现已补充；用户复测三个均出现。其余召唤技能及已有召唤物时的具体限制仍受原技能状态和服务端行为影响。

签将原生普通攻击 `11003、11004` 的攻击动作和前置判断段最大距离配置均为 `15`；原动作段为 `6`、判断段为 `3`。服务端已热重载，客户端包已更新，用户反馈普通攻击距离变远。这是签将技能配置，不限定掠夺者之剑。

## 同步技能

玩家技能九星 `3002`、壬鱼（克）`3021`、勾陈 `3003`、风雷震巽 `3004`、腾蛇 `3083`、无妄 `3071`，对应召唤物测试技能 `60000–60005`。先等待玩家本次施法的首个有效命中，随后给有自身有效目标的签系提交任务；事件另有约 0.48 秒延迟。勾陈取第一个有效命中，不累计多目标伤害；玩家没有有效命中则不提交。

匹配到同步命中记录时，伤害输入为玩家首个有效命中结算返回值的签兵 80%、签将 50%、签王 30%，向下取整；目标后续吸收等处理会影响最终扣血。未匹配时回退原模板，原模板配置为单段物理攻击 100%，并非完整玩家技能公式。同步技能未完整复制控制、状态和多段效果；每只召唤物的复制记录只消费一次，多目标和连续快速施法等边界需进一步验证。九星同步特效、伤害及复制记录已验证；用户反馈三类伤害顺序符合当时设置，签将后续从 60% 改 50% 按用户要求未另测。

提交同步前尝试打断签系原生技能 `11000、11003、11004、11006、11007、7265–7277`，不主动打断同步技能 `60000–60005`。逐次诊断显示斗煞曾阻挡同步，加入打断列表后的复测仍有同步技能彼此占用导致的拒绝。详见下文“历史专题：同步施法与伤害”。

## 伤害、仇恨与冷却

- 每只存活有效签系使主人在已接入的普通命中路径造成的伤害输入增加 30%、受到的伤害输入减少 30%；三只分别为 190%、10%，减伤最多 100%。侍从和灵宝不计入。用户复测计数为签兵、签将、签王三只；主人减伤具体扣血比例仍未单独核对。
- 签系召唤物在已接入的普通命中路径受到伤害减少 90%。用户反馈承伤明显降低，诊断记录到触发；具体最终扣血比例和所有伤害来源尚未逐项验证。
- 命中仇恨倍率：签兵原值 50%、签将 100%、签王 300%（3 倍）。同步伤害覆盖之前的仇恨基数不一定与最终伤害一致；用户反馈签王更容易拉住，三类仇恨入口均有诊断记录。
- 遁甲术·顺行 `3062、3065`、增寿 `3063`、锐利 `3064` 在装备 `60075` 并写入新冷却时为 20 秒。用户反馈三个名称冷却约 20 秒；快照不能证明顺行两个 ID 均单独验证。已有冷却不会主动重置。

## 主动索敌演进与通神启用

以下先保留早期调查与方案，2026-11-06 后续实际采用通神启用，结果见本节末尾。

早期需求：使用遁甲术·顺行切换签系自动搜索并攻击附近怪物，再次使用关闭。当前尚未实现或部署。服务端主包中顺行技能为 3062、3065，原本会驱散并免疫签系不良状态，无召唤物时还会召唤签兵；技能原冷却配置为 120 秒，装备 60075 时现有钩子调整为 20 秒。要作为开关使用，需明确替换原有效果并解决再次使用的冷却限制，客户端技能说明也需同步。

服务端存在 `CServerChaNPC::SearchEnemy`、`SetTargetID` 和仇恨接口，但已检查的 `SearchEnemy` 路径包含随机寻找玩家，不能直接作为搜索怪物的实现。仍需确认安全的周边怪物枚举、敌对判定、签系目标分配及主人离线、跨场景和召唤物重建时的状态管理，完成隔离和游戏内验证后才能部署。

主动找怪的候选底层入口：服务端 `n_whcmn::whsightlist2D::SearchBox` 支持区域枚举回调，现有 `G_SearchEnemy(int)` 回调通过 `CScnSpaceS::GetObj` 将对象 ID 转为对象，并检查类型、死亡、视野和距离，随后涉及仇恨处理。它使用全局 `g_SearchEnemyThis` 且面向原 NPC 索敌，不能直接认为适合签系寻找怪物；回调参数、对象类型、阵营和目标提交路径仍需隔离测试。尚未实现或部署签系主动找怪。

进一步只读定位：`G_SearchEnemy` 接收对象 ID，通过 `CScnSpaceS::GetObj` 获取对象，并先检查对象类型值为 2、未死亡及非坐骑车辆，再进行距离、可见性和虚函数敌对判断。当前服务端另有 `CServerCha::IsMyEnemy(CCha*)`（0x9197cc）、`CServerChaNPC::SetTargetID(int)`（0x94f308）和 `CServerCha::ChgHate`（0x91cc52）符号；这些是候选接口，尚未确认签系运行时的虚函数实现、怪物和友方对象的具体分类，也未证明写入目标后 AI 一定追击。直接复用原回调还会操作全局索敌上下文，不能仅凭符号直接挂接。

`SearchEnemy` 的区域搜索半径来自 `GetSearchDis()` 的属性 35；实际搜索使用该值减 1，小于 0 时跳过区域搜索。它还可能根据 NPC 配置走随机玩家分支，并通过全局 `g_SearchEnemyThis` 将当前索敌者传给回调。签系运行时该属性、对应 NPC 配置分支和安全调用时机尚未核验；不能仅调用函数就认定能找到怪物。

## 历史专题：一键三召唤与属性继承

> 原文来源：签系一键三召唤测试.md。此章节记录当时的实现与测试，历史表述以日期为准。

### 效果和范围

装备挂机神剑（物品 ID 60074）时，成功使用一次受支持的签系召唤技能，服务端尝试补齐签兵、签将、签王各 1 个。每种在旧类型和新类型之间合计最多保留 1 个；已有其他种类则不再重复召唤。没有装备该武器时，保持原有召唤逻辑。

这是按武器 ID 识别的测试效果，并非可配置的通用装备词条。其入口独立于该武器已有的最大生命值百分比伤害、吸血和召唤物同步九星逻辑。

### 实现方式

源码：`scripts/native/summon_three_signs_test.c`。在已核对版本的游戏进程中，拦截技能事件 `20014`，先执行原始召唤，确认产生新的召唤物后，再使用同一套服务端召唤事件生成缺少的两种。使用各自的召唤类型、NPC 和资源标识，不改变全局召唤上限，也不需要替换客户端资源包。

原召唤的等级用来选择其他两种的 NPC：选择不高于原召唤等级的最高已有档位；若该类型最低档位仍高于原召唤等级，则使用该类型最低档位。签将最低档位为 25 级，签王最低档位为 56 级，因此低等级技能补出的召唤物可能高于原召唤物。

## 参考指南：奇门签系召唤共存

> 原文来源：奇门签系召唤共存修改指南.md。此章节记录当时的实现与测试，历史表述以日期为准。

### 用途

把本文和目标游戏文件、服务器访问方式一起交给 AI，指导它在实际版本中排查并实现奇门签系召唤物共存。目标是让签兵、签将、签王等不同签系召唤能按需求同时存在；保留各自正确的召唤物身份、技能效果、冷却和到期行为。本文描述的是修改方法和验证标准，不是可直接覆盖所有版本的成品补丁。

### 给执行修改的 AI

先读取本文、相关项目文档和实际客户端/服务器文件，再判断当前版本如何限制召唤物。不要因为旧补丁使用了某个状态 ID、召唤类型、二进制偏移或完整 DPK，就在当前版本照抄。用当前包中的技能 ID 和引用链确认根因；版本不匹配或证据不足时，先完成静态分析并报告具体缺项，不要猜测写入。

执行修改前，记录用户期望的共存范围和数量规则：

- 哪些签系技能/召唤类型之间应当共存？同一种能否重复召唤？
- 每次施法召出几个？数量上限是每一种单独计算，还是全部签系共用总上限？
- 切图、进副本、死亡或重新登录时，召唤物应如何处理？存在时间是多少？
- 各技能冷却是否必须独立？召唤物自己的技能栏和身份是否应保持原样？

若用户只说“多个签系共存”，默认只解除不同签系之间的互斥，并尽量保留原技能的召唤对象、施放次数、冷却、召唤物技能栏和生命周期。对数量上限、切图保留、召唤物全局删除行为等额外变化，应从实际版本和已有配置确定，不能把某个补丁的副作用当作默认目标。

### 一、先建立当前版本的技能与召唤链

1. 确认实际客户端 `mb.dpk`、服务器主包、服务器动态包、相关散文件以及服务端二进制的路径、大小、修改时间和 SHA-256。以当前连接配置、服务器运行目录和文件为依据，不以历史路径或旧日志代替核实。
2. 查看 `doc/召唤物自定义功能说明.md`、`doc/召唤物列表.csv` 及用户提供的补丁/参考文件。区分参考数据与当前正在运行的数据。
3. 分别从客户端、服务端主包和动态包提取签系相关记录，按技能 ID、方法 ID、触发 ID、召唤类型 ID 和召唤物角色/外形 ID 建立引用关系。常见相关资源包括：
   ```text
   skill/skill_data_npc_2.txt
   skill/method_data_npc_2.txt
   skill/trigger_npc_2.txt
   pet/summon_type.txt
   ```
   实际资源名和目录以当前包为准。若签系技能存在于其他职业表、外形表或服务端逻辑中，也纳入追踪。
4. 对每个签系技能逐项检查：技能自身状态限制、施放后附加到玩家的状态、方法链中的召唤事件/驱散事件、触发器的召唤类型、召唤类型的数量/跟随/存在时间字段，以及服务端是否另有按召唤类型删除旧召唤物的逻辑。
5. 比较能共存与不能共存的情形。优先用数据证据证明拦截点，例如第二种签系施放时客户端提示、状态限制字段、方法中的删除事件、同一召唤类型的数量规则或服务端清理调用。不要只根据技能文字下结论。

### 二、逐层解除互斥

在当前版本查明根因后，仅修改实际造成互斥的层。可能涉及以下一种或多种机制：

#### 技能施放限制

检查签系技能定义中的施法者状态限制、目标状态限制及其相邻字段。如果特定状态代表“已有签系召唤物”，需确认该状态的实际含义和引用范围，再清除此限制或换成不会互相排斥的条件。不能不经确认就删除整列状态条件，因为其中可能包含职业、武器、场景或其他必要限制。

#### 施放后的玩家状态

检查技能方法/效果链是否在施放后给玩家附加互斥状态。若有，确认它是否专为签系互斥服务，并从目标签系方法中移除或改为各签系独立的标记。保留同一技能本来需要的其他增益、消耗、动作和失败处理。

#### 召唤与驱散事件

检查签系方法链是否先调用召唤物驱散/删除事件，再执行新召唤。若该事件会清除其他签系召唤物，只对签系技能取消该驱散调用，或将清理条件收窄到同一技能/同一召唤物。不要全局移除其他职业或普通召唤技能的正常清理逻辑。

#### 召唤类型与数量池

确认触发器中的召唤类型 ID 如何参与数量限制和清理。多个技能共用召唤类型可能让它们进入同一数量池，也可能被引擎视作同类而互相覆盖。根据当前版本行为，决定是否为签兵、签将、签王保留独立类型，或使用统一类型并明确设置共享上限。

不能仅为“能同时存在”就把所有签系触发器改成同一个类型。统一类型可能造成共享数量上限、身份/清理范围变化，或使“每种最多 N 个”的预期实际上变为“全部总共最多 N 个”。需核查 `pet/summon_type.txt` 的最大数量、跟随主人和存在时间字段，并在游戏内分别测试。

#### 服务端删除逻辑

如果配置表都没有互斥，而运行结果显示引擎仍在生成新召唤物时清除旧召唤物，应定位服务端实际调用的删除逻辑及其条件。优先寻找按签系类型/召唤物 ID 选择性保留或删除的改法。只有确认无法局部修复且用户接受影响范围时，才考虑禁用全局召唤删除入口。

二进制修改必须验证服务器版本、函数/偏移、预期原始字节和反汇编上下文。特定补丁曾把 `TTYGZS_d.so` 的 `CServerCha::Summon_Del` 在偏移 `0x923216` 处从 `55 89 e5` 改为 `31 c0 c3`，使整个函数返回、不再删除召唤物。这是**特定版本的全局改动参考**，不是通用偏移，也不是首选方案。全局禁用可能让其他召唤物或脚本无法按原逻辑清理，需评估所有受影响功能，制作二进制备份并安排停服/重启验证。原字节不匹配时必须停止，不能强写。

### 三、保留其他技能和自定义配置

- 不用参考补丁里的完整 `server_mb.dpk` 或 `client_mb.dpk` 覆盖当前整包，除非已确认这是用户指定的完整基线且其他自定义内容均不需要。完整包可能缺少用户后加的技能、学习记录、商城或其他补丁。
- 以当前客户端包、服务器主包、服务器动态包各自为底包。分别修改需要的签系资源；检查散文件是否覆盖 DPK 中的同名表，并确认主包/动态包加载优先级。
- 当前工作台已有自定义召唤技能 ID `3126`，及相关方法 ID `30422`–`30424`、触发 ID `302247`。改动前后检查这些 ID 和相关学习/导师/技能栏配置仍存在，且其冷却和召唤对象没有被签系修改串用。
- 若修改的是签系技能冷却、触发 ID 或方法 ID，逐项确认没有和巨甲遁、六合签或工作台自定义技能共用标识，除非用户明确要求共用。
- 客户端与服务端资源可能不同。逐包读取和修改；不要从客户端拷贝整行/整表覆盖服务器，反之亦然。

### 四、制作和校验包

本工作区的工具位于 `scripts/` 目录。先查看当前版本工具帮助，再使用：

```sh
python3 scripts/unpack.py /path/to/mb.dpk -o /path/to/unpacked
python3 scripts/repack.py /path/to/current.dpk path/in/package.txt /path/to/edited.txt -o /path/to/next.dpk
```

`repack.py` 一次替换一个已存在的资源并输出新包，不要将输出写回输入。多张表连续替换时，每一步使用前一步输出。

修改文本资源时保留原编码、制表符、空列、列数、换行和无关行。每次改动都留下逐行差异和变更 ID 清单。生成包后：

1. 重新提取修改过的表，核对预期字段、签系技能集合、触发/方法引用、数量规则和存在时间。
2. 检查所有新旧 ID 无冲突，引用都能解析，未出现重复记录或悬空方法/触发 ID。
3. 对客户端、服务端主包和动态包分别做全资源校验；记录每份包的修改前后 SHA-256。
4. 检查包内其他技能和用户自定义配置未意外改变。若二进制有修改，独立运行版本/字节检查，并保留可恢复的原文件备份。
5. 校验通过后才准备部署包。静态校验通过只能说明包结构和数据关系符合检查，不能声称已在游戏中生效。

### 五、部署和游戏内验收

每次部署前分别备份客户端包、服务器主包、服务器动态包及任何二进制文件，记录路径、哈希、属主和权限。采用同目录临时文件替换并保留服务器文件权限；不要原地改写运行进程映射的 `.so`。

签系技能配置写入文件后，服务器进程通常不会自动重新加载已载入的技能表；需要按该服务器既有维护流程重启世界服。客户端包替换后要完全退出游戏进程，再重新启动。除非当前工作台功能明确实现了自动重启，不要假设它已重启服务端。

用测试角色依次验证：

1. 单独施放每种签系技能，确认召唤对象、数量、动画、技能栏和冷却仍正确。
2. 施放第二种签系技能后，确认第一种召唤物仍在；轮流施放所有签系组合。
3. 连续施放同一种，确认单种上限和全局上限与用户预期一致，并验证是否互相占用名额。
4. 检查切图、进出副本、死亡、召唤物到期和重新登录的行为是否符合用户要求。
5. 检查普通宠物、其他职业召唤物、工作台自定义召唤技能 `3126` 及其宠物技能栏，排除全局删除逻辑带来的副作用。
6. 查看服务端日志，确认没有技能表解析错误、未知 ID、崩溃或异常召唤清理。

若任何验收失败，停止继续扩大改动，按本次部署对应的备份恢复客户端和所有服务器文件，恢复原权限后重启并确认回到修改前行为。

### 六、参考补丁中的具体线索

下载目录曾有 `寻仙补丁参考/奇门签系召唤共存补丁_v1.0`。它可作为签系字段定位样本，不是所有版本的安装包。该版本的检查脚本针对以下现象做了自检：

- 技能 ID `13307`–`13331` 和 `13549`–`13573` 的部分签系数据；
- 技能/方法中的状态限制和召唤事件；
- `skill/trigger_npc_2.txt` 中的召唤类型；
- `pet/summon_type.txt` 中类型 `349` 的最大数量和跟随主人字段；
- `Summon_Del` 的二进制改动。

该参考补丁把签系召唤类型统一为 `349`，设置类型总上限为 15，方法链每次施放调用三次召唤事件，并把召唤存在时间设为 600 秒。其安装脚本会整体覆盖服务端主包，且禁用全局召唤删除函数。把它用于当前工作台时，直接覆盖会丢掉当前补丁包未包含的自定义技能 `3126` 等配置；应只提取必要签系字段差异合入当前包，并重新评估全局 `.so` 修改的副作用。

利用这个样本时，先对照补丁说明、`tools/check_mb.py`、补丁 DPK 和当前 DPK 四方数据；确认当前表结构和对应技能 ID一致，再决定是否采用其中字段值。不能仅因校验脚本显示“8 项通过”，就推断当前服务器版本兼容或游戏内行为正确。

### 修改完成后的汇报

向用户说明根因证据、改了哪些包/表/ID、共享或单类数量上限、是否更改服务端二进制、备份与生成文件位置、静态校验结果，以及是否已部署、重启和游戏内验收。把“文件已生成”“服务端已加载”“游戏内已验证”分开报告；未验证的效果明确标为待验证。
