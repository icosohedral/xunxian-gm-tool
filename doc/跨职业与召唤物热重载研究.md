# 跨职业技能与召唤物热重载研究

研究日期：2026-10-27。目标是游戏服务端持续运行；允许玩家退出客户端、替换客户端包、重新登录和重新召唤。

本文保留扩展方案与证据记录。后续实现已完成并在同日执行原生重载：跨职业技能表 210、211；召唤物关联表 209、210、211、500、1351、1352 与 `reloadskill`。两条线路的表数据回读通过，PID 未改变。工作台按当前子标签选择热重载范围；客户端仍需替换包、重新登录，召唤物需重新召唤。

## 已确认的共用入口

当前服务端存在原生命令 `reloadexcel 表ID`，入口 `CServerCmd::_i_srad_reloadexcel`（`TTYGZS_d.so` 相对地址 `0x985b20`）。它调用 `CExcelTableMng::ReloadTable(int)`（`0xc614ea`），再调用 `MBCfgMngs::ReloadExcel(int, bool)`。

`MBCfgMngs::ReloadExcel` 在当前版本仅对 1620（在线奖励）有额外刷新分支，不能假定它会为学习、NPC 或召唤物自动重建派生缓存。

`CExcelTable::Reload()`（`0xc60d98`）先 `RemoveAll()`，再按记录的资源路径载入并创建索引。因此失败时不能只恢复磁盘文件，还必须重载旧数据并验证内存；也必须检查使用者是否长期持有旧行指针。

可以复用现有 GMS 本机管理协议、游戏主线程命令队列、服务器包共享缓存、临时散文件覆盖、版本校验及事务恢复框架。扩展时只增加固定的表 ID 白名单，不开放任意管理命令。

## 跨职业技能

### 实际修改与运行时读取

当前 `scripts/skill_limits.py::patch_dpk_changes` 修改：

| 文件 | 用途 | 服务端读取情况 |
| --- | --- | --- |
| `skill/skill_learn.txt` | 学习条件、职业限制等 | 表 211，运行时已载入 |
| `skill/npc_teach_skill.txt` | 导师可教技能列表 | 表 210，运行时已载入 |
| `skill/skill_cha_ls/yx/fs/fzs.txt` 中对应分表 | 客户端职业技能列表 | 当前服务器表 202 实际只载入 `skill/skill_cha.txt`，不能把分表与表 202 混为一谈 |

在普通线只读检查了表路径：211 对应 `mb/skill/skill_learn.txt`，210 对应 `mb/skill/npc_teach_skill.txt`，202 对应 `mb/skill/skill_cha.txt`，表 202 当前为 7 行。

`CPlayerDataMngS::LearnSkill(int)`（`0x7dbe48`）在学习请求中查询表 211；需要检查当前导师时查询表 210 并核对其技能数组，后面再次查询表 211 检查条件。这是直接读取全局表的代码证据，说明重新载入这两张表可以改变后续学习请求的判断；尚未通过真实角色学习完成验收。

### 建议实现

1. 完成现有写包与回读校验。
2. 从服务器当前主包提取 211、210 对应的原始文件，临时部署到已核实的磁盘覆盖路径。
3. 对普通线和交易线分别执行固定的 `reloadexcel 211`、`reloadexcel 210`。
4. 验证表行数、目标技能的职业字段，以及导师技能数组内容。现有重载器只检查整型单元，必须增加数组内容检查，不能只检查行数。
5. 成功后清理临时文件；任何一步失败时，两张表与两条线一并恢复。
6. 玩家替换客户端包并重进，重新打开导师窗口，再学习目标技能。

只调整学习规则时不必额外执行 `reloadskill`；如果同次操作也新增或修改技能定义，再合并执行。取消允许学习不会自动删除角色已经学会的技能，这属于另一项角色数据操作。

## 召唤物自定义

### 表与实例的关系

| 文件或表组 | 表 ID | 处理思路 |
| --- | --- | --- |
| 游侠、NPC 的技能、方法、触发表等 | 现有 45 张技能表范围 | 使用已实现的 `reloadskill` |
| `object/cha_skill_choose.txt` | 500 | 修改自选技能组后定向重载 |
| `summon/summon_skill.txt` | 1351 | 修改默认技能、技能栏顺序后定向重载 |
| `summon/summon_skill_index.txt` | 1352 | 新增技能索引时定向重载，并替换客户端包 |
| 学习、导师、升级表 | 211、210、209 | 只有实际发生相关变更时重载 |
| `object/cha_list.txt` | 82 | 仅补入原本缺失的导师角色记录时需要；应单独验证角色缓存影响 |
| `object/cha_fight.txt`、分身战斗属性表 | 88、1435 | 当前召唤自定义通常不改这两张表，无需为了切换召唤物而重载全部属性 |

代码证据：

- `CCha::ListNpcSkill()`（`0xae855a`）查询角色表 82，根据外形读取技能选择表 500，将技能 ID 放入角色实例的 `std::vector<int>`。技能组是实例持有的数据，不能认为重载表 500 就立即更新已经召出的角色。
- `CCha::ListNpcSkillUnit(int)`（`0xae8462`）还会访问技能单元表 501，支持技能组中的间接引用。当前自定义通常修改 500；只有实际修改 501 时才应将其纳入重载范围。
- `CServerCha::InitSummonStraw(CServerCha*)`（`0x9189a2`）按召唤物战斗能力 ID 查询表 1351，设置默认技能与手动技能列表。因此新召唤实例有读取新技能栏配置的入口。
- `CChaDataMngBase::GetExcel()`（`0xaf336e`）按角色 ID 查询表 82；`CNpcDataMngBase::GetFightDataInt(int)`（`0xb2b072`）存在读取 88 与 1435 的分支。仍不能据此认定所有属性缓存都会自动刷新。
- 当前 `_ensure_friend_cha_list` 在导师记录已存在且外形一致时直接返回原数据，缺失时才补入；它不负责重写所有 NPC 属性。

### 建议实现

1. 玩家先退出客户端，或至少收回召唤物并结束战斗。
2. 记录本次实际修改的资源清单，区分客户端资源与服务器已加载资源，避免盲目重载所有表。
3. 暂时部署本次需要的散文件；对普通线和交易线重载技能选择与技能栏等关联表，再执行 `reloadskill` 重建技能定义与方法数据。涉及表 82 时单独处理，不能直接宣称与技能表同样安全。
4. 验证选择技能 ID、技能栏数组顺序、冷却、召唤触发器关联角色 ID，以及涉及的角色记录均与主包一致。表 1352 含字符串和图标字段，需扩展相应校验，不能只依赖现有整数检查。
5. 清理临时散文件并保存最近一次完整成功状态；失败时恢复整个关联表组及两条线路。
6. 玩家替换客户端包，重新登录并重新召唤，让新的召唤物实例初始化技能组和技能栏。此流程不要求已有召唤物原地更新。

该方案不会因为重载配置而给怪物增加新的 AI 逻辑；仍使用当前自选技能方案。也不应自动全服收回其他玩家的召唤物。

## 验证次序与未完成事项

优先验证跨职业两张规则表：范围小，学习处理函数直接查询它们。选一个角色尚未学会的技能，验证“允许后可学习”，再用另一个未学技能验证“取消后不能学习”，同时确认两个游戏进程未重启。

随后验证切换到已有角色的召唤自定义：检查外形、技能组、技能栏顺序和冷却，并确认重新召唤后使用新配置。最后再测试需要向表 82 补入新导师记录的情况，排查其他 NPC 对旧表行的引用。

本次证据来自工作台修改代码、服务端符号与反汇编及运行内存路径检查。数组/字符串校验、关联表事务恢复现已实现，跨职业、召唤物部分失败恢复均有自动化测试。现有角色配置的实际重载与内存校验已通过；角色真实学习、施放及重新召唤后的游戏表现尚需客户端验收。表 82 当前与主包一致，实际测试未触发其重载；补入全新导师角色的分支尚未做运行验收。

服务端版本约束沿用《技能热重载实现说明》中的四个二进制 SHA-256，不应在未核实其他版本时直接照搬地址或表布局。
