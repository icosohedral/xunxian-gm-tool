# 单机服务端数据库清理方案

本文记录 2026-11-01 对当前服务端数据库的只读调查和建议流程，供后续核对，不代表已经执行清理。账号 `test` 明确保留；其他账号，包括 GM 账号 `111`，是否保留须在执行前逐一确认。角色、账号和交易数据不可仅凭账号名或表名推断为无用。

## 现状

- 游戏数据主要分布在 `xunxian_84`、`xunxian_ims_84`、`xunxian_gis_84`、`xunxian_lba_84`。调查时四个库的基础表均为 InnoDB，表和索引合计约 187 MB；数值会随数据和统计信息变化。
- `common_accounts` 有 28,590 个账号，`common_characters` 有 26,908 条角色记录，其中 197 条标记删除。这是调查时的精确计数，不代表所有账号或角色均可删除。
- 数据库版本为 MySQL 5.5.47，`innodb_file_per_table=1`，未开启 binlog。没有 binlog 时，不能依靠现有日志恢复到两次备份之间的任意时间点。
- 服务器有 MySQL 5.5 自带的导出工具：`/opt/xxserver/database/tools/mysql-5.5.47-linux2.6-x86_64/bin/mysqldump`。不得在命令行、日志或文档中暴露数据库凭据。
- 工作台「删除角色」只修改 `common_characters.mark_delete` 和 `delete_time`；它不是永久删除，也不清理账号和其他关联数据。在线写库可能被游戏进程的内存状态覆盖。

## 涉及的数据

| 范围 | 主要位置或例子 | 处理原则 |
|---|---|---|
| 登录账号 | `xunxian_ims_84.malay_playerinfo` | 保留 `test` 登录信息；其他账号先确认，不直接删除整表。 |
| 游戏账号 | `xunxian_84.common_accounts` | 保留账号 ID、属性和状态；GM 权限相关属性也在此处。 |
| 账号资产 | `point_partition_0`、`common_acctstorage`、账号称号等 | 按账号名或账号 ID 分别核对；不要将账号资产当作某个角色独有数据。 |
| 角色及存档 | `common_characters`、`common_char_whstream`、属性、任务、技能、物品、宠物等表 | 列出每个保留角色的 ID 和相关记录；二进制存档不可拆分推测。 |
| 社交及组织 | 好友、师徒、伴侣、家族、门派 | 角色 ID 可能在关系的任意一端；先检查保留角色的关系和组织身份。 |
| 交易及邮件 | 市场、拍卖、邮件、附件、交易流水 | 核对未完成交易和待领取物品，避免破坏共享状态或造成资产丢失。 |
| 服务与历史 | `xunxian_gis_84`、`xunxian_lba_84` 及各类历史记录 | 先确定用途、关联和保留期限，不根据名称批量删除。 |

角色表中既有 `common_`，也有 `entire_`、`delete_`、`unavailable_` 等不同名称的表；它们是实际数据表，具体读写及恢复规则尚未全部验证。角色关系也可能使用 `at_char_id`、`ps_char_id`、`rela_char_id` 等字段，不能只搜索 `char_id`。数据库未发现针对账号和角色表的相关触发器，不能假设删除主记录会自动完整清理依赖。

## 建议流程

1. **确定范围。** 列出所有要保留的账号；`test` 必须保留。明确 `111` 和其他账号的去留。列出保留账号的所有角色及资产，记录不确定的数据；在范围确认前不清理。
2. **停服并备份。** 让角色完全退出并正常停止游戏服务，备份四个游戏库的表结构、数据和必要数据库对象；将备份复制到服务器之外。在线 `--single-transaction` 可提供 InnoDB 数据库快照，但不能保证包含尚未从游戏进程内存写回的数据。
3. **验证备份。** 检查导出过程、文件大小和校验值；在隔离数据库试恢复，并核对 `test` 的账号、角色、资产和存档。备份包含登录信息及资产数据，应限制访问。
4. **生成清单。** 在隔离副本中按保留账号 ID、账号名和角色 ID 梳理直接和间接关联，记录每张候选表的保留／待清理数量；特别核对邮件附件、拍卖、门派、家族和关系两端。不能依赖 MySQL 估算行数当作精确计数。
5. **隔离演练。** 先确认历史表是否被使用，再针对明确属于待清理账号的记录设计并执行演练；共享数据单独处理。不要对正式库直接运行 `DROP DATABASE`、`DROP TABLE` 或未限定范围的 `DELETE`、`TRUNCATE`。
6. **验证游戏。** 使用隔离环境检查 `test` 登录、所有角色、背包装备、宠物、技能、任务、副本、仙玉、账号仓库、邮件及组织关系；检查引用是否悬空，并与清理前的清单比较。
7. **正式实施。** 只有清理清单、备份和隔离验证均完成，并确认保留范围后，才安排正式停服处理。留存操作记录、前后计数和回滚方案。

删除行不一定立即缩小磁盘文件。即使开启 `innodb_file_per_table`，空间回收也需要单独评估表重建、额外磁盘空间、锁和停服时间；不为节省少量空间盲目执行 `OPTIMIZE TABLE`。

## 未决问题

- 除 `test` 外要保留哪些账号，尤其是 `111`？
- `test` 的邮件、市场交易、门派、家族和社交关系是否依赖其他待清理角色？
- 各业务和副本表中角色 ID、物品 ID、账号名的完整引用，以及二进制存档内部的数据结构是什么？
- 历史日志、副本表是否仍有服务端、网站或工作台读取？
- 正式恢复是否需要重建缓存、清除在线锁或重新启动相关服务？这些操作应先在隔离环境验证。

在上述问题解决前，不应把本文作为可直接执行的永久删账号脚本。
