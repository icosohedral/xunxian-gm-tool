# 服务端增量写包优化（待完成）

状态：待实现。本文记录后续方案，不代表工作台已经支持服务端写包。

## 目标与现状

将修改后的表在服务端重新压缩、加密并写入 DPK，减少修改队列同步时整包上传的流量与等待时间。

当前队列在本机准备客户端、服务端主包和动态包的临时副本，按队列顺序叠加修改，然后将有变化的服务端 DPK 整包上传、校验和替换。并非把所有资源全部解包重建，但网络传输仍是完整 DPK。

拟改为：本机生成修改后的表，只上传表文件和修改清单；服务端以当前包的临时副本为基础，完成压缩、加密、写回、校验和发布。客户端包继续在本机生成。

目前观察到一次召唤物应用的服务端同步阶段约 33 秒，包含上传、指纹核对、替换、校验和清理，没有上传单独耗时。优化收益需通过分阶段计时确认，不能把这段时间全部归因于上传。

- [ ] 每个目标包只准备一份临时副本，将该包所有表的修改集中写入；现有逐表写入实现仍可能产生中间文件，是否进一步消除需另行验证。
- [ ] 在服务端完成压缩、加密和资源写回，支持现有允许的块链扩展规则。
- [ ] 回读所有变更表，核对解码内容、包结构及新增武器记录；全部通过后才进入发布。

服务端仍需在磁盘复制 DPK。首阶段优化目标是减少网络整包传输，实际耗时应包含磁盘复制和压缩开销。

### 4. 发布服务端包

- [ ] 发布前再次核对原包指纹，防止准备期间发生其他修改。
- [ ] 为有变化的包各备份一次，并使用同文件系统内的替换方式提交临时包。
- [ ] 校验最终正式包 SHA-256，返回主包、动态包的最终指纹与分阶段耗时。
- [ ] 记录事务状态，处理请求超时或断线后的结果查询，避免重复执行新增武器等操作。
- [ ] 保留现有磁盘文件提交保护：多包替换中途失败时，尝试恢复已替换的磁盘包并报告结果。多个文件的替换不应宣称为单次原子操作。
- [ ] 不自动热重载或重启；沿用队列完成后的热重载／手动重启提示。

### 5. 更新本机共享缓存与客户端包

- [ ] 本机以同一基线和同一批表更新服务端主包、动态包缓存，避免同步成功后又下载完整包。
- [ ] 验证本机与远端写包结果能否逐字节一致，并将压缩实现及参数固定在兼容版本；对最终包计算 SHA-256 核对。
- [ ] 若不能保证一致，不得伪造缓存指纹；明确缓存失效及必要时重新下载的处理方式。
- [ ] 客户端持久工作包仍在本机按队列合并，最终只下载一份客户端 `mb.dpk`。
- [ ] 服务端已提交而本机更新失败时，返回明确的已提交状态并保留恢复资料，避免重试导致重复新增。
- [ ] 成功、失败及过期事务的临时文件按明确策略清理，保留恢复所需文件的位置和提示。

## 失败处理边界

- 生成、上传或服务端临时写包失败：不发布正式包，返回具体阶段和错误。
- 基线指纹不符：停止，不覆盖服务端新内容。
- 磁盘提交中途失败：沿用文件提交保护并报告是否恢复成功。
- 热重载失败：不恢复运行时旧表，不自动重启服务端，由操作者决定后续操作。
- 网络断开导致提交结果未知：先查询事务状态，再决定重试，不能直接重新新增武器。
