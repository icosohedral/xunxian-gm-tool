# 门派重启消失修复补丁原理

本文根据下载目录中的 `寻仙补丁参考/门派重启消失修复补丁` 说明、安装脚本、`p_player.c` 和 `patch_so.py` 整理。它记录补丁的设计思路和代码行为，不代表已经在当前服务器版本上验证兼容。

## 修复的现象

补丁针对服务器重启后门派成员与角色关联丢失的问题。常见表现是门派界面为空；也可能显示门派名，但成员职位被重置，掌门无法执行掌门操作。

## 补丁的两部分

### 1. 玩家登录后恢复门派关联

补丁在玩家登录加载完成后的 `LoadOK_Player_Login` 中调用 `Player_GuildRestore(iPlayerGID)`。它通过 `G_GetPlayerGuild` 检查当前角色是否已有门派：

- 已有门派：调用 `RefreshGuildUI()` 刷新门派界面，并记录 `org_ok` 日志。
- 当前没有门派：遍历服务器门派，仅当恰好找到一个“成员数大于 0”的门派时，才尝试恢复关联。
- 恢复时：以系统身份调用 `addorgmember`，随后再次检查角色门派并刷新界面。成功或失败分别记录 `rebind_ok`、`rebind_fail`。

补丁作者对根因的解释是：服务端加载门派时只会给当时在线的成员回写角色内存中的门派 ID；服务器启动时通常没有玩家在线，所以登录时角色内存中的门派 ID 仍为 0，登录数据便没有发送正常的门派信息。登录回调负责补上这一步。

这是补丁文档提出的机制解释；当前目录没有包含服务端源码或运行时跟踪，不能据此独立证明每个服务器版本的门派加载行为完全相同。

### 2. 避免恢复关联时职位被改成门徒

恢复脚本使用的 `addorgmember` 最终会调用引擎函数 `CGuildUnitS::DirectAddMember`。补丁认为该函数存在一条无条件写入，把成员职位字段设为 `2`（门徒）。

`bin/patch_so.py` 对服务器 `TTYGZS_d.so` 的固定偏移 `0x6B086F` 进行修改：

| 状态 | 字节 | 含义 |
|---|---|---|
| 原始 | `c6 40 31 02` | 将 `2` 写入 `[eax+0x31]`，覆盖职位字段 |
| 补丁后 | `90 90 90 90` | 4 条 NOP，不执行这次职位写入 |

这样配合登录时的重新绑定，意图是在恢复门派关联时保留原职位。普通游戏内申请和审批入派据补丁说明走 `AcceptMember` 代码路径，不受这个改动影响。

## 实际执行顺序

1. 玩家完成登录加载，触发 `LoadOK_Player_Login`。
2. `Player_GuildRestore` 检查角色当前的门派关联。
3. 若关联缺失且代码找到唯一一个有成员的门派，则执行 `addorgmember`。
4. 引擎将角色重新加入/关联到门派；二进制补丁阻止 `DirectAddMember` 强制覆盖职位。
5. 脚本再次检查绑定结果，刷新门派界面并写入 `GUILD_RESTORE` 日志。

## 代码可见的限制和风险

- 脚本只在有且仅有一个成员数大于 0 的门派时恢复。没有门派或有多个候选门派时会跳过，日志分别记录 `no_cand` 等状态。
- `Player_GuildRestore` 检查的是“角色当前是否已关联门派”，然后以唯一候选门派作为目标；代码没有显式查询持久化成员表来确认这个角色原本就是该门派成员。因此，未绑定的非成员角色登录时也可能触发 `addorgmember` 尝试。需结合当前 `addorgmember` 的实现和数据库成员记录确认其实际影响。
- `Player_GmExec` 调用 `G_DealPlayerTstStr(0, szCmd)`，补丁代码注释说明参数 `0` 会跳过 GM 权限检查、以系统身份执行。这个能力不应暴露给玩家可控输入。
- 补丁只让 `DirectAddMember` 不再强制写职位，并没有指定一个新的职位值。补丁说明提醒：通过 GM 命令添加从未属于该门派的新成员时，职位可能为 `0`。
- `install.sh` 会完整替换运行目录中的 `p_player.c`。该文件不仅有门派恢复代码，还包含卦象、Buff 等其他登录逻辑。若服务器已有定制版本，应比较并合并必要函数，避免覆盖原功能。
- `patch_so.py` 使用固定偏移和固定原始字节，只适用于相匹配的引擎版本。原始字节不匹配时必须停止，不能强行改写。
- 补丁包不含已修改的 `.so`，而是直接修改服务器现有库。修改后要重启服务端才能让新库生效；更换正在运行进程使用的二进制文件时，应按服务器维护流程安全停服或采用适当的原子替换方案。

## 判断补丁是否生效

按补丁 README 的方法，在重启后检查最新运行日志：

- `p_player.c:Error` 无输出，表示脚本未报告编译错误。
- `fb_menpai` 日志应显示门派数据加载成功。
- 门派成员登录后检查 `GUILD_RESTORE`：`org_ok` 表示原关联存在并刷新界面；`rebind_ok` 表示脚本认为重新绑定成功；`rebind_fail` 表示绑定失败。
- 核对 `guild_members.class` 等服务器实际使用的职位数据，确认掌门、长老等职位未被降级。

这些日志和数据库检查可验证脚本执行结果；最终仍应让相关成员登录，检查游戏内门派界面、成员职位和掌门操作。

## 回滚

补丁的 `rollback.sh` 会尝试恢复首次安装前备份的 `TTYGZS_d.so` 和 `p_player.c`，然后需要重启服务端。回滚前应确认备份路径和安装状态文件对应本次安装；若 `p_player.c` 安装前不存在，脚本会删除运行目录中的该文件，以恢复使用 DPK 内置脚本的状态。
