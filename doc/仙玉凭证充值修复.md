# 仙玉凭证充值修复

## 问题

使用仙玉凭证后道具被消耗，但账号仙玉余额没有增加。以仙玉凭证（10000仙玉，物品 ID 49983）为例，道具使用配置调用效果 98，向点券服务发送增加 10000 点券的请求；100000 仙玉凭证也使用同一类效果。

服务端点券代理将负数金额请求一律视为购买退款，要求找到对应的原扣款记录。凭证充值没有原扣款，因此被拒绝，余额没有变化。

## 修复方式

2026-11-04 修改服务端 `/opt/xxserver/bin/transactions.py`：在原退款匹配逻辑之后，对金额为 `-10000` 或 `-100000` 且请求末尾为 `43 00` 的请求，按充值处理并增加账号余额。此前使用 `native_ext` 低 16 位识别凭证的规则不可靠：实际观察到该值在不同运行中分别为 `0x60`、`0x16` 和 `0x00`，因此当前规则不再检查该字段。

原有的退款匹配、余额上限和请求去重逻辑继续生效；不符合该特征且没有对应扣款的负数请求仍会被拒绝。该特征来自已观察到的请求，不能证明其他交易不会使用同样的金额和报文后缀；尚需验证其区分能力及游戏内完整流程。

仓库中的 `scripts/voucher_proxy_repair.py` 可对已核对的原始代理源码生成补丁；它不会自动部署到服务器，且会拒绝不匹配或已打补丁的源码。原文件备份为 `/opt/xxserver/bin/transactions.py.bak.voucher-20261104`。修复写在磁盘上，正常重启保留；重装、恢复旧备份或更新覆盖该文件后须重新核对并部署，再重启使代理加载。

旧版规则曾使用真实数据库执行回滚事务测试，覆盖两种金额、重复请求去重和普通负数请求拒绝；该结果不能作为当前规则的验证。2026-11-04 15:57 的游戏内测试使用了旧规则，因编号变为 `0x00` 被拒绝，之后已向 `test` 补偿 10000 仙玉，余额核对为 1012928。更正后的规则已部署并重启至服务就绪，但尚未完成事务测试及游戏内验证。15:49 的其他失败请求尚未补发，需先核实实际消耗数量。
