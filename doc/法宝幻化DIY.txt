"模型位置"其实分两层：真正的配置在客户端的两张外观表里；服务端只记一个"外观编号"。下面这些是我们这套（服务端 + 梦回客户端 3.5.x）实际查到的结果，你朋友可以照着做。

一、整条链路（4 张表）
顺序	表（在 mb.dpk 里）	位置	关键内容
① 道具	item/item_list*.txt	服务端 + 客户端	法宝幻化道具的物品类是 604，神兵幻化是 603；"使用属性"指向一条使用规则
② 使用规则	item/item_use.txt	服务端 + 客户端	效果类型 = 18（对装备附魔），参数1 = 配方ID
③ 配方	life/recipe_serve.txt	服务端 + 客户端	附魔类型 = 2；物品类型限制填 101（法宝）或 100（武器）；"附魔后走光效果" = 外观编号 N
④ 外观	equip/equip_fb.txt（法宝）<br>equip/equip_wq.txt（武器）	只在客户端	决定编号 N 显示成什么模型
以"法宝幻化：熊猫"为例：道具 19921 → 规则 705（效果 18，参数1 = 1005）→ 配方 1005（走光效果 = 5）→ 客户端 equip_fb 里外观 5 号对应的那一列。

二、模型具体写在哪：客户端外观表
equip/equip_fb.txt（法宝）：

每一行对应一个法宝模型。第 1 列"装备ID"等于道具表里那件法宝的**"模型ID"**。
第 2 列"男装备串"是这件法宝平时的模型，比如 e_fba_203。
第 N+2 列是外观 N（列号从 0 数）：外观 1 在第 3 列（武士刀），外观 5 在第 7 列（熊猫），依此类推。最后一列是"附加前缀"（天罡 / 地煞的光效）。
格子里填的是模型串。天罡法宝那一行会带前缀，比如 p_fbtg_01*e_fba_603。
equip/equip_wq.txt（武器）： 规律一样，也是第 N+2 列对应外观 N，第 2 列"标准效果"是武器平时的模型。

所以"幻化成某个职业的法宝"这样做：

先在道具表里找到那件法宝，拿到它的"模型ID"。
到 equip_fb 里找"装备ID"等于这个模型ID 的那一行，第 2 列就是它的模型串。
选一个空着的外观列，整列每一行都填上这个模型串。天罡 / 地煞的行要保留各自的前缀。
新建一个配方，"走光效果"填这个外观编号。再加一条规则（效果 18，参数1 = 新配方）和一个道具（物品类 604）。
道具、规则、配方要在服务端和客户端都加；外观表只改客户端。
三、提醒你朋友注意的几点
先核对自己的版本。 上面的列号和空列是在梦回客户端上查到的，不同客户端可能多列、少列。最稳的核对方法：拿任意一个现成幻化道具，从道具 → 规则 → 配方的走光效果 → 外观表的列，完整走一遍，确认"列号 = 编号 + 2"成立。
优先用现成没人用的列。 我们这边空着的是：法宝第 16、22 号，武器第 3、4、6、9、10、29、33 号。判断方法：配方表里没有任何配方用到这个编号。另外，"拂尘"那一列虽然有道具，但它指向的配方 98 根本不存在，所以实际上也是空的。
在表末尾加新列客户端认不认，还没在游戏里验证。 要加的话只能加在最后，不要插在中间，否则后面的列整体错位。
编号不要回收。 已经幻化过的法宝会一直记着这个编号，换成别的模型，它们的外观会跟着变。
模型串怎么找到实际文件还没查过。 e_fba_xxx 这类是客户端模型资源的名字，实际文件在客户端资源包里，具体路径我没查。只要沿用表里已有的模型串，就不需要碰资源文件。
注意替换的方式。 改外观表时只替换那一列的格子，其他字节保持原样，换行符要保留 CRLF。改之前先备份客户端的 mb.dpk。
