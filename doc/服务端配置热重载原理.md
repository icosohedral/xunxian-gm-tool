# 服务端配置热重载原理

本文说明服务端原生命令、C++ 函数、表 ID 与资源文件之间的关系，不涉及管理页面或界面操作。记录依据为已核对的服务端符号、反汇编、包索引及运行时表检查，整理日期为 2026-10-27。

## 1. 为什么改了 DPK，运行中的配置不会自动更新

配置存在三个层次：

1. 磁盘来源：`mb.dpk` 中的表，或磁盘上的同路径散文件。
2. 进程中的配置表：原生加载器解析文件后建立的行数据和索引。
3. 派生数据与游戏实例：技能方法、被动数据、商城目录，以及已经创建的角色、召唤物和物品等。

修改磁盘文件只改变第一层。运行中的进程仍然使用第二层或第三层数据，因此需要主动调用重载入口。重启服务端会整体重新初始化；热重载则在保留进程的情况下，重新读取指定配置并执行必要的重建函数。

“表已经重新载入”不等于“所有已有实例已经重新初始化”。不同功能必须分别分析表的使用者和缓存。

## 2. 原生命令如何进入游戏进程

当前版本在服务端本机提供 GMS 管理通道 `127.0.0.1:3000`，通过以下命令向指定线路转发：

```text
gmcmd_2_gzs 1,reloadskill
gmcmd_2_gzs 9,reloadskill

gmcmd_2_gzs 1,reloadexcel 211
gmcmd_2_gzs 9,reloadexcel 211
```

这里的 `1`、`9` 分别是当前部署的普通线和交易线编号，其他部署应核对自己的线路。以上是原生管理协议中的命令正文，不能直接当成 Linux Shell 命令执行。

管理通道把指令交给游戏原生命令队列执行，不需要外部程序向游戏内存写入数据，也不需要从外部线程直接跳入 C++ 函数。每个线路进程有各自的表和缓存，只重载一条线路不会更新另一条。

当前协议帧为：

```text
AA 55 + uint32_le(正文长度) + 正文 + 55 AA

握手正文：F1 + uint32_le(0)
握手回应：FB 01 0A 00 00 00

请求正文：F2 + uint32_le(请求标识) + 00 + ASCII命令 + 00
回应正文：FC + uint32_le(相同标识) + 状态字节 + GB18030文本 + 00
```

实际调用前可经同一通道发送 `help reloadskill`、`help reloadexcel`、`help reloadxyshopitem` 核对命令支持情况。当前只确认了 `reloadexcel 单个表ID`，不能假定一次传入多个 ID 的语法有效。

## 3. 通用表重载：reloadexcel

已确认的调用链：

```text
CServerCmd::_i_srad_reloadexcel
    ├─ CExcelTableMng::ReloadTable(int 表ID)
    │    └─ CExcelTable::Reload()
    │         ├─ RemoveAll()
    │         └─ 按该表登记的资源路径重新载入并建立索引
    └─ MBCfgMngs::ReloadExcel(int 表ID, bool)
```

当前 `TTYGZS_d.so` 中记录的相对地址：

| 函数 | 相对地址 |
| --- | --- |
| `CServerCmd::_i_srad_reloadexcel` | `0x985b20` |
| `CExcelTableMng::ReloadTable(int)` | `0xc614ea` |
| `CExcelTable::Reload()` | `0xc60d98` |

表 ID 来自包内 `index_list.txt` 的注册关系，不是文件名的编号，也不是技能 ID、物品 ID。一张运行时表可能由多个文件组成，例如物品表 41。

当前版本的 `MBCfgMngs::ReloadExcel` 只观察到表 1620（在线奖励）的专门刷新分支。不能据此假定任意表重载后都会自动重建关联对象或其他模块的派生缓存。

成功回执示例：

```text
ReloadExcel: 211 OK!
```

由于 `Reload()` 先清空再读取，读取失败可能已经影响运行中的表。只把磁盘文件改回去不能自动修复已经清空或部分更新的内存数据。

## 4. 重载时为什么需要散文件

散文件是从包中取出的原始配置文件，例如：

```text
/opt/xxserver/runtime/xx/shm/TTYGZS/mb/skill/skill_learn.txt
/opt/xxserver/runtime/xx/shm/TTYGZS/mb/object/ride_list.txt
/opt/xxserver/runtime/xx/shm/TTYGZS/mb/item/item_list.txt
```

已核对版本的文件管理器运行在模式 2，优先读取磁盘文件，再回退到包文件。因此可以把目标表部署到原生加载器登记的散文件路径，再调用原生命令读取。

这解决两件事：表重载需要正确的文件来源；此外，运行中的进程可能仍持有旧 DPK 的打开文件描述符，磁盘上替换同名包后，旧描述符仍可能指向旧文件，直接重载不一定读到新包。

基本过程为：

```text
取得当前服务端包中的完整目标表
    → 放到原生散文件路径
    → 原生命令重新解析
    → 校验运行时表与派生数据
    → 清理本次临时散文件
```

表已经解析进入内存后，删除本次临时散文件不会撤销内存中的结果。长期遗留散文件则可能遮蔽后续的新包。原位置已有散文件时，应保留其来源和内容，不能当成临时文件直接删除。

文件的编码、列结构、表头和索引登记的起始行都必须保持正确。例如 `skill/trigger_methodunit1.txt` 存在首个物理行为空的情况，不能先随意去空行再解释起始行。

## 5. 技能定义：reloadskill

入口是 `CServerCmd::_i_srad_reloadskill`，主要执行：

```text
清理场景中正在运行的技能、效果单元
    DelAllSkillAndMehtodUnit()

重读技能定义相关表
    CMethodGroupDataMng::ReloadSkillTable()

重建方法与方法单元
    CMethodDataMng::LoadMethod(1)
    CMethodDataMng::LoadMethodUnit(1)

重新建立技能组及被动数据
    CMethodGroupDataMng::Load()
    CMethodGroupDataMng::ReloadPassive()
```

`DelAllSkillAndMehtodUnit` 的拼写按已记录符号保留。`reloadskill` 不只是循环执行 `reloadexcel`，还包含技能系统的派生数据重建，所以不能用只重载一张技能表来等价替代。

### 5.2 重载后的边界

原生成功文字为 `ReloadExcel:OK!`。该入口会覆盖部分中间错误文字，回执不能单独证明所有表和派生数据均正确。

重载会清理正在运行的技能效果，不保证已有冷却、角色界面或召唤物自动刷新。应分别检查运行内存，并在客户端验收施放行为；客户端显示所需配置仍需更新客户端资源。

## 6. 学习规则与跨职业学习

| 表 ID | 文件 | 内容 |
| --- | --- | --- |
| 210 | `skill/npc_teach_skill.txt` | 导师可教授的技能数组 |
| 211 | `skill/skill_learn.txt` | 学习条件和职业限制等 |
| 209 | `skill/skill_levelup.txt` | 技能升级相关配置，发生变更时另行重载 |

只改导师和学习条件时，对每条线路执行 `reloadexcel 210`、`reloadexcel 211`，无需仅为这些规则额外执行 `reloadskill`。

依据是 `CPlayerDataMngS::LearnSkill(int)`（当前相对地址 `0x7dbe48`）在处理学习请求时查询表 211；需要导师校验时查询表 210 的技能数组，后续再检查学习条件。重载改变的是之后请求所读取的全局规则。

取消学习权限不会自动删除角色已经学会的技能。客户端职业列表分表 `skill_cha_yx/ls/fs/fzs.txt` 与服务端表 202 也不能混用：当前运行时表 202 实际来源为 `skill/skill_cha.txt`。

## 7. 召唤物：技能定义与关联表共同更新

| 表 ID | 文件 | 对应内容 |
| --- | --- | --- |
| 82 | `object/cha_list.txt` | 角色定义；补入角色或修改相关记录时才需考虑重载 |
| 500 | `object/cha_skill_choose.txt` | NPC 技能选择组 |
| 1351 | `summon/summon_skill.txt` | 召唤物默认技能、技能栏等配置 |
| 1352 | `summon/summon_skill_index.txt` | 召唤技能索引及相关显示配置 |
| 209、210、211 | 上述升级、导师、学习表 | 发生关联修改时重载 |
| 45 张技能定义表 | 第 5 节列出的资源 | 技能与方法变化使用 `reloadskill` |

完整的关联范围为 45 张技能表加 7 张关联表，共 52 张。并非每次都必须执行 52 条命令：技能定义由一次 `reloadskill` 负责，其余用定向 `reloadexcel`；角色表 82 应在确有变化时单独处理。

关键读取函数：

| 函数 | 当前相对地址 | 已确认行为 |
| --- | --- | --- |
| `CCha::ListNpcSkill()` | `0xae855a` | 查询表 82、500，将技能放入实例的 `std::vector<int>` |
| `CCha::ListNpcSkillUnit(int)` | `0xae8462` | 访问表 501，处理技能单元的间接引用 |
| `CServerCha::InitSummonStraw(CServerCha*)` | `0x9189a2` | 查询表 1351，初始化默认技能与手动技能列表 |
| `CChaDataMngBase::GetExcel()` | `0xaf336e` | 按角色 ID 查询表 82 |
| `CNpcDataMngBase::GetFightDataInt(int)` | `0xb2b072` | 存在查询表 88、1435 的分支 |

表 501 为技能单元关联表，仅在实际修改时另外纳入；表 88（`object/cha_fight.txt`）与 1435（分身战斗属性表）不属于上述默认 52 张范围。单纯切换召唤角色，不代表这两张属性表发生变化。

技能组已复制到召唤物实例中，因此重载后需要重新召唤。重载技能选择表也不会为怪物凭空增加一套 AI，AI 行为是否存在以及是否由召唤实例使用，是另一条逻辑。

## 8. 骑宠配置

| 表 ID | 文件 | 对应内容 |
| --- | --- | --- |
| 84 | `object/ride_connection.txt` | 乘骑连接配置，包括乘骑施法相关设置 |
| 85 | `object/ride_list.txt` | 骑宠记录，包括移动速度、场景与飞行等字段 |

对每条线路分别执行：

```text
reloadexcel 84
reloadexcel 85
```

这两张表通过通用加载器更新；没有因此证明所有正在骑乘的对象立即刷新。已有对象可能保存初始化时的值，需下坐骑后重新骑乘验证。

## 9. 物品定义与新增武器

当前服务端主包将以下三个文件登记为同一个运行时表 41：

```text
item/item_list.txt
item/item_list2.txt
item/item_list3.txt
```

三个来源共同构成表 41，不能只放置一张修改文件而忽略其他来源。应准备与当前主包一致的三文件，再对每条线路执行 `reloadexcel 41`。

代码依据为：

```text
CItemMngBase::GetExcel(int item_id)
    → CExcelTableMng::SafeGetLine(41, item_id)
```

因此重载后的表可供后续按物品 ID 查询及新物品创建使用。当前动态包索引的表 41 只登记 `item/item_list.txt`，重载来源必须以运行进程实际登记的主包三文件为准，不能仅看动态包索引。

这一结论针对物品定义表，不能推导出已经生成的物品实例的所有属性都会刷新。新增武器仍需客户端具备对应记录、图标与模型资源，再在游戏内发放验证。

## 10. 商城：reloadxyshopitem

商城使用独立散文件：

```text
/opt/xxserver/runtime/xx/shm/TTYGZS/dynamicmb/xy_shop_item.txt
```

当前主包和动态包的 `index_list.txt` 没有将此文件登记为可直接用 ID 重载的表。商城使用专用入口：

```text
CServerCmd::_i_srad_reloadxyshopitem
    ├─ CExcelTableMng::ReloadTable(67)
    ├─ CShopMngS::XYShopDestroy()
    ├─ CShopMngS::XYShopBuild()
    └─ CShopMngS::XYShopReload()
```

入口在当前版本的相对地址为 `0x97b5b8`。`XYShopDestroy()` 清理旧商城数据，`XYShopBuild()` 重建商城目录，`XYShopReload()` 还会构造 `SSTC_EXP1_XYSHOP_RELOAD` 通知，用于商城刷新。

注意：入口虽然先调用 `ReloadTable(67)`，但当前包索引的表 67 是 `life/recipe_serve` 资源，不能把 67 解释成 `xy_shop_item.txt` 的表 ID。单独执行 `reloadexcel 67` 不等价于商城重载；关键在后续商城管理器的销毁、重建和刷新流程。

保存并校验商城散文件后，对每条线路执行 `reloadxyshopitem`。成功回执为：

```text
reload xy_shop_item OK!
```

## 11. 多类配置一起重载的原则

1. 先合并目标资源及表 ID，同一表只重新读取一次。
2. 先加载技能所依赖的学习、召唤等关联表，再执行一次 `reloadskill` 重建技能派生数据。
3. 商城保留专用 `reloadxyshopitem`，不能只靠通用表重载代替。
4. 分别更新所有相关线路并核对结果，不能把一条线成功视作全服完成。

减少重复命令可以节省时间，但不能绕过专用模块的重建函数。原生命令也不是跨表、跨进程的一次原子事务；失败可能留下部分更新状态。

## 12. 如何证明热重载成功

应至少核对以下层次：

- 文件来源：目标资源、原生路径、字节校验值与预期一致。
- 运行时配置：表来源、行数、ID、目标字段、数组与字符串内容一致。
- 进程身份：PID 和进程启动标识未变化，确认没有通过重启获得结果。
- 游戏行为：技能施放、学习、重新召唤、重新骑乘、发放物品与商城刷新符合预期。

仅命令回执成功或仅行数一致都不充分。只读运行内存可以验证实际载入的表，但仍不能完全替代派生缓存与游戏行为验收。

此前已确认技能定义、学习规则和召唤关联表可以在 PID 不变时更新运行内存，也观察到商城上架、下架后的原生重载成功。骑宠与新增物品的具体已有实例刷新行为，仍应单独在游戏中验收，不能从通用表加载成功直接推断。
