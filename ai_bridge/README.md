# 寻仙 AI 桥

把游戏客户端收到的每个服务器数据包实时发到本机，让程序（例如 AI）不用看画面，也能知道游戏里正在发生什么。

## 原理

- 网络分发函数 `0x56b250` 按消息首字节分成两路：
  - `>= 0x80` 是游戏包。交给 `CTTY3DGameMng::Receive`（`0x460b50`），处理完后调用录像器的 `AddMsg(包指针, 长度)`（`0x4a2d30`）。不录像时这个函数直接返回，但每个游戏包都会经过它。
  - `< 0x80` 是命令包。交给另一个处理器，不经过 `AddMsg`。实测只在登录、选角、进入游戏时出现。
- 钩子装在两处，两类包都能收到，而且互不重复：
  - `AddMsg` 开头（`0x4a2d30`）收游戏包；
  - 分发函数的 `< 0x80` 分支（`0x56b329`）收命令包。
- 本项目编译出一个替身插件 `gcassist.so`：
  - 客户端照常通过 `client2_cfg.txt` 的 `PlugIn` 配置加载它；
  - 3 个插件导出转发给改名后的原插件 `gcassist_real.dll`，游戏功能不受影响；
  - 加载时在 `AddMsg` 开头装一个跳转钩子，把每个包复制进 4MB 环形缓冲区；
  - 后台线程用 TCP 发到 `127.0.0.1:47800`（可用环境变量 `XXBRIDGE_PORT` 改）。
- 录像器会故意跳过 16 种包类型，钩子在过滤之前，所以这些包也能收到。
- 装钩子前会核对函数开头的 6 个字节。只适用于 SHA-256 `59e50674…` 这个版本的 `tty3d.exe`，版本不对时只写日志、不改代码。

背景分析见 [doc/游戏录像格式分析.md](../doc/游戏录像格式分析.md)。

## 使用

需要先安装 32 位 Windows 交叉编译器：

```bash
brew install mingw-w64
```

编译并安装到客户端。安装脚本会把原 `gcassist.so` 改名为 `gcassist_real.dll`，并备份为 `gcassist.so.orig`：

```bash
./install.sh
```

在 Mac 上开接收端，再正常启动游戏。先开哪个都可以，插件每秒重试连接一次：

```bash
python3 receiver.py --out packets.jsonl
```

每个包输出一行 JSON：

```json
{"seq": 19, "tick": 1234567, "time": "19:20:41", "bType": 129, "name": "move", "size": 28, "hex": "81c50381…"}
```

- `bType` 是包类型；`name` 是根据录像分析起的名字，`?` 表示还没有命名。
- `hex` 是原始包内容，字段解析待补。

卸载，恢复原插件：

```bash
./uninstall.sh
```

## 实时动态悬浮窗

`viewer/` 是一个 macOS 小程序「寻仙实时动态」，可以代替 `receiver.py` 作接收端。它把收到的包解析成中文事件，显示在一个悬浮在游戏上方的半透明窗口里：

- **顶部状态栏**：连接状态、包数、当前场景、视野内对象数，以及自己的坐标和血蓝。
- **事件列表**：
  - 战斗：施放技能（显示技能名和目标）、受到的伤害、选中目标、进入和脱离战斗、死亡、冷却；
  - 收获：获得经验、获得或失去物品；
  - 出现/离开：角色、怪物、场景物件进入和离开视野；
  - 状态：状态增删；
  - 系统：进入场景、天气、系统消息（例如 GM 物品发放）。
- **分类开关**：移动、数值、其他、未解析这几类量大，默认隐藏。
- **原始包日志**：每次运行都把所有原始包写到 `~/Library/Logs/XunxianViewer/packets-日期时间.jsonl`，方便事后分析新的包类型。

编译后复制到客户端的 `launcher/` 文件夹：

```bash
viewer/build.sh
```

编译时会用 `export_names.py` 从客户端 `mb.dpk` 导出技能、角色、状态、场景、物品、场景物件的名称表 `names.json`（不提交到仓库），打包进 App。

字段偏移是这样来的：

- 录像里的包，把录像 XML 和同一批包的原始字节逐个对照，自动推出偏移；
- 录像里没有的包，看客户端序列化函数 `0x48f3f0` 里对应类型的反编译代码。

已知含义如下：

| 包 | 含义 | 字段 |
|---|---|---|
| `0xca` | 进入场景 | 场景 @2，自己的对象 ID @6，坐标 @8/@12 |
| `0xb4` | 角色或怪物进入视野 | ID @1，表 ID @3，等级 @8，血量% @9，坐标 @12/@20，名字 GBK @44 |
| `0xbc` | 场景物件进入视野（采集点、可交互物件，例如鸟窝、凝香草、纺车） | ID @1，物件 ID @3（对应 `object/still_list.txt`），坐标 @5/@9 |
| `0xd0` | 对象移除（物件被采集或离开视野） | ID @2 |
| `0x80` | 死亡或消失 | ID @1，类型 @3：1 = 死亡（只在血量降到 0 后出现），2 = 消失（NPC 离开、走出视野、尸体消失） |
| `0x88` / `0x87` | 技能开始 / 结束 | ID @1，技能 @3，目标 @5 |
| `0x86` | 选中目标 | ID @1，目标 @3 |
| `0x8f` | 状态增删 | ID @1，类型 @3（0 添加，1 移除，2 同步），状态 @4 |
| `0x81` / `0x83` | 移动 / 转向 | ID @1；移动坐标 @4/@12，速度 @24；转向角度是 @3 的低 15 位 |
| `0xb6` | 属性值 | 属性编号 @1，数值 @3。已知：7 = 生命（推测），8 = 蓝量，35 = 金钱，41 = 当前经验值 |
| `0x85` | 对象标志 | ID @1，类型 @3，数据 @4。类型含义见下 |
| `0xbf` | 冷却 | 编号 @2，剩余秒数 @4 |
| `0x91` | 头顶飘字 | ID @1，数值 @3，类型 @7。实测 6 = 怪物受到的伤害，50 = 自己获得的经验（推测，击杀豺后固定 +124） |
| `0xcc` | 物品 / 背包操作 | 操作类型 bWork @1，各类型字段见下 |

`0xcc` 的 bWork，字段名来自客户端序列化函数 `0x49f880`：

| bWork | 字段 | 含义 |
|---|---|---|
| 0 | byBox @2，wExcelID @3，wAutoID @5，耐久 @7/@9，byNum @11 … | 背包新增一条物品记录 |
| 1 | wAutoID @2 | 删除物品记录 |
| 2 | wAutoID @2，byNum @4 | 数量变化 |
| 3 | wSrcAutoID @2，wDestAutoID @4 | 移动 / 合并 |
| 4 / 5 | wExcelID @2，byNum @4，byBox @6 | 获得 / 失去物品的通知 |
| 6 | wAutoID @2，bDataType @4，dwData @5 | 物品属性变化 |
| 9 | wExcelID @3，wMchtID @5，iItemNum @7，iCDLeft @15，iPrize @23 … | 商店物品列表（打开商店时成批到达） |
| `0x89` | 装备外观 | ID @1，@3 最低位是类型、其余位是栏位，装备编号 @4 |

`0xb6` 里金钱和经验按无符号 32 位读，因为经验已经接近有符号上限：

- 金钱的单位是铜。1 砖 = 100 金，1 金 = 100 银，1 银 = 100 铜，所以 1 砖 = 1000000 铜。窗口显示成"1砖23金45银67铜"这样的格式；金钱变化时，「收获」里会出现增减。
- 当前经验总量显示在顶部；击杀获得的经验看 `0x91` 头顶飘字。

`0x85` 对象标志的类型，根据实测数值推断：

| 类型 | 含义 | 依据 |
|---|---|---|
| 8 | 血量 % | 小统领的值从 91 逐个升到 96 |
| 9 | 蓝量 % | 和属性 8（蓝量）同步变化 |
| 1 | 战斗状态（推测） | 自己和豺都会在 0 / 1 之间切换 |
| 0 | 所在区域 | 值 980 是 `area_info` 里小桑村【一】的 ID |
| 20 / 26 | 召唤物 / 主人 | 分别是宠物的 ID 966 和主人的 ID 965 |
| 4、12、34 等 | 不明 | 4 跟随侍从移动出现，34 在怪物进入视野时出现 |

窗口里有一个「其他」分类，默认隐藏，放的是结构已知、但含义不明或价值不大的包：

- 同步包 `0xba`：录像器也会跳过；
- 物品数据同步 `0xcc` / `0xd4`：登录时成批出现，编号连续；
- 各种标志和计时：`0xb7`、`0xb8`、`0x8e`、`0x91` 等；
- `0x85` 中含义不明的标志类型。

「未解析」只剩完全不认识的包类型。2026-11-13 的两次测试数据里都已经是 0。

## 文件

| 文件 | 作用 |
|---|---|
| `bridge.c` | 替身插件：钩子、环形缓冲区、TCP 发送线程 |
| `gcassist.def` | 插件导出转发到 `gcassist_real.dll` |
| `receiver.py` | Mac 上的接收端，输出 JSONL |
| `build.sh` / `install.sh` / `uninstall.sh` | 编译、安装、卸载 |
| `export_names.py` | 从 `mb.dpk` 导出名称表 |
| `viewer/` | 实时动态悬浮窗：`XunxianViewer.swift`、`Info.plist`、`build.sh` |

运行日志写在客户端 `release/ai_bridge.log`。

## 验证情况

2026-11-13 用录像播放（`tty3d.exe -film <录像文件名>`）测试。播放时的包同样经过 `Receive → AddMsg`，所以不需要登录：

- 收到 150 个包，序号连续，包括 25020 字节的角色数据大包；
- 19 种包类型的数量与录像文件内容完全一致；
- 客户端运行和退出正常。

同日在真实登录、连服务器的游戏中实测，用登录器自动登录 `test` 账号：

- 148 秒收到 1658 个包，平均每秒 11 个，序号连续、没有丢包；
- 游戏运行流畅，没有感觉到卡顿；退出正常；
- 共 32 种包类型，比录像多 13 种，包括录像器会过滤掉的 `0xba`；还有序列化函数不认识的 `0xf1`、`0xff`；
- 能直接看到的内容举例：
  - 周围角色的名字（叮叮、神力道人等）；
  - 侍从称号"小统领的侍从"；
  - 系统物品发放消息 `<title:GM 物品发放><additem:wExcelID=6159,byNum=1>`。

## 已知限制与后续

- **字段未解析**：接收端只输出原始字节。下一步是按录像里的字段名逐个解出偏移，或者直接调用客户端自带的字段序列化函数 `0x48f3f0`，把包变成带字段名的 JSON。
- **需要状态层**：交给 AI 之前，还需要一层"当前世界状态"，汇总周围有谁、位置、血蓝、状态、冷却。
- **反作弊**：客户端带有 `tersafe.dll` 和 `AntiBot`，钩子可能被检测到。只建议在自己的服务器上使用。
- **缓冲区满会丢包**：没有开接收端时，包会在 4MB 缓冲区里累积，满了就丢弃，并在日志中记录丢弃数量。
